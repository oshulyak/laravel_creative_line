# Lesson 24 - Карточка поста как компонент: лайки в ленте и удаление своего поста

Цель урока: превратить разметку карточки поста, продублированную на двух страницах, в собственный Vue-компонент, повесить на него рабочий лайк и кнопку удаления своего поста. Серверной работы здесь мало, и вся она — «дописать недостающее»: маршрут удаления, проверка «пост мой» и одно поле в ресурсе. Основное новое — клиентское: свои компоненты, пропсы вниз, события (`emit`) вверх, вложенный компонент внутри компонента и вопрос, как не тащить событие через все уровни вручную.

По пути разбираются: `props` и `emits` как публичный контракт компонента; `$emit` в Options API; `provide`/`inject` как способ достучаться до предка через любое число уровней; fallthrough-атрибуты (`class` на компоненте); наблюдатель за пропом и почему без него локальная копия протухает; частичная перезагрузка Inertia `router.reload({ only: [...] })`; и почему решение «удалять или нет» принимает сервер, а Vue только рисует кнопку.

Отправная точка — состояние после 23-го урока: лента, страница поста с лайком и «Мои публикации» работают, но карточка поста написана дважды (в `Feed/Index.vue` и в `Profile/Personal.vue`), лайк в ленте — мёртвый индикатор, а удалить пост можно только из админки.

## 1. Карта урока

Что появляется:

| Файл | Роль |
| --- | --- |
| `resources/js/Components/Post/ItemPost.vue` | карточка поста: автор, анонс, лайк, кнопка удаления |
| `resources/js/Components/Post/DeletePost.vue` | вложенный компонент — только кнопка удаления и запрос |
| `tests/Feature/ClientPostDestroyTest.php` | тест на правило «удалять можно только своё» |

Что правится:

| Файл | Что меняется |
| --- | --- |
| `routes/client.php` | маршрут `client.posts.destroy` |
| `app/Http/Controllers/Client/PostController.php` | метод `destroy()` |
| `app/Http/Resources/Post/PostResource.php` | поле `can_delete` |
| `app/Http/Controllers/Client/ProfileController.php` | `with('author')` и `withExists()` — карточке нужно то же, что ленте |
| `resources/js/Pages/Client/Feed/Index.vue` | разметка карточки уезжает в компонент, добавляется `provide()` |
| `resources/js/Pages/Client/Profile/Personal.vue` | то же самое |

Команды (Vue-файлы создаются руками — генератора для них нет):

```shell
php artisan make:test --phpunit ClientPostDestroyTest
```

Папка `resources/js/Components/Post/` — новая. У Breeze папка `Components/` плоская (`PrimaryButton.vue`, `Modal.vue`, ...), потому что там лежат универсальные элементы формы. Наши компоненты знают про предметную область — про пост, — поэтому им нужна своя подпапка. Правило простое: универсальное лежит в корне `Components/`, привязанное к сущности — в папке с именем сущности.

Имя `ItemPost`, а не `PostItem`, — так сформулировано задание; держать одно соглашение важнее, чем спорить о порядке слов. Оба файла в PascalCase: это конвенция Vue для однофайловых компонентов, и она же позволяет писать `<ItemPost />` в шаблоне.

## 2. Почему серверной работы почти нет

Стоит проговорить до кода, иначе покажется, что урок клиентский целиком.

**Лайк в ленте.** Маршрут `client.posts.likes.toggle` и метод `PostController::toggleLike()` написаны в 23-м уроке, `FeedController::index()` уже отдаёт `likes_count` и `is_liked`. Не хватало ровно одного — кнопки. В 23-м уроке мы сознательно оставили в ленте индикатор без клика («лента — страница чтения»); теперь требование другое, и меняется только клиент.

**Удаление.** Вся работа лежит в `PostService::destroy()` из 21-го урока: он в транзакции удаляет картинки (и файлы с диска), отвязывает теги и лайки, удаляет комментарии и сбрасывает версию кэша админского списка. Клиентскому контроллеру остаётся дописать одно правило — «пост мой» — и позвать сервис. Это и есть отдача от того, что логика в своё время уехала из контроллера: второй потребитель получил её бесплатно, вместе с инвалидацией кэша, о которой он даже не знает.

Дописать на сервере нужно поэтому только маршрут, метод-обёртку, поле `can_delete` в ресурсе и пару строк в `ProfileController` — чтобы карточка на обеих страницах получала одинаковый набор данных.

## 3. Маршрут и `Client\PostController::destroy()`

IN `routes/client.php` — внутри той же группы `auth`, рядом с `client.posts.show`:
```php
    // DELETE, а не POST: глагол уже описывает действие, и админский маршрут
    // admin.posts.destroy объявлен так же. Адрес совпадает с показом поста —
    // различает их метод, это и есть REST.
    Route::delete('posts/{post}', [PostController::class, 'destroy'])
        ->whereNumber('post')
        ->name('client.posts.destroy');
```

IN `app/Http/Controllers/Client/PostController.php` — третий метод класса:
```php
    /**
     * Удаление своего поста.
     *
     * Алиас HttpResponse в импортах нужен из-за коллизии: Response в этом файле —
     * это Inertia\Response, его возвращает show().
     *
     * @see \App\Http\Controllers\Admin\PostController::destroy()
     */
    public function destroy(Request $request, Post $post): HttpResponse {
        // Единственное отличие от админского destroy() — проверка авторства.
        //
        // 403, а не 404 как в show(): существование поста уже не тайна, пользователь
        // видел его в ленте. Скрывать нечего, отказать нужно честно.
        //
        // Сравниваем author_id с id ПРОФИЛЯ, а не пользователя: posts.author_id
        // ссылается на profiles.id. Профиля может не быть — тогда ?-> даст null,
        // сравнение с author_id (он NOT NULL) будет ложным, и получится тот же 403.
        abort_unless($post->author_id === $request->user()->profile?->id, 403);

        // Тот же сервис, что и в админке. Он снимает связи, стирает файлы картинок
        // и двигает версию кэша списка — клиентскому контроллеру не пришлось написать
        // ни строчки этой логики.
        PostService::destroy($post);

        // 204 No Content: тела у ответа нет, клиент и так знает, что удалял.
        return response()->noContent();
    }
```

Импорты, которых в файле ещё нет:
```php
use App\Services\PostService;
use Illuminate\Http\Response as HttpResponse;
```

Отдельный `FormRequest` не нужен по той же причине, что и у `toggleLike()`: тела у запроса нет, всё приезжает из URL и из сессии.

Проверка авторства в контроллере — временное решение, ровно как `abort_unless()` в `show()`. Её место — `PostPolicy::delete()`, и тогда в контроллере останется `Gate::authorize('delete', $post)`, а правило станет доступно и админке (где сейчас удалить может любой залогиненный — известная дыра из 21-го урока). Политики идут дальше по курсу.

## 4. `can_delete` в `PostResource` — кто решает, показывать ли кнопку

Кнопку удаления видно только у своих постов. Значит, клиенту нужно знать, свой это пост или нет. Способа два.

Первый — сравнить на клиенте: положить id профиля в общие пропсы (`HandleInertiaRequests::share()`) и писать в шаблоне `post.author_id === $page.props.auth.profile.id`. Работает, но правило авторизации переезжает в JS, и таких сравнений станет столько, сколько кнопок.

Второй — отдать готовый ответ с сервера. Его и берём: решение принимает PHP, Vue только рисует.

IN `app/Http/Resources/Post/PostResource.php` — рядом с `is_liked`:
```php
            // Ответ на вопрос «может ли текущий пользователь удалить этот пост».
            // Правило пока простое — «пост мой», — и живёт оно в одном месте,
            // а не в шаблоне каждой страницы.
            //
            // N+1 здесь нет, хотя выглядит опасно: $request->user() возвращает один
            // и тот же объект User на весь запрос, а связь profile загружается лениво
            // один раз и запоминается на этом объекте. На страницу из десяти постов
            // придётся один дополнительный запрос, а не десять.
            //
            // ?-> дважды: в API-контексте пользователя может не быть вовсе,
            // а у пользователя — профиля.
            'can_delete' => $this->author_id === $request->user()?->profile?->id,
```

Ключ отдаётся всегда, без `whenHas()`/`whenLoaded()`: это дешёвое вычисленное булево, а не связь, ради которой пришлось бы идти в базу. В админском ответе он тоже появится — там его никто не читает, и это не повод усложнять ресурс условием.

Важно: `can_delete` — подсказка интерфейсу, а не защита. Кнопку можно не рисовать, а запрос всё равно отправить руками. Поэтому то же правило продублировано в контроллере (п. 3), и настоящая проверка — там. Формулировка, которую стоит запомнить: **клиент решает, что показать; сервер решает, что разрешить.**

## 5. `ProfileController::personal()` — чего не хватало карточке

Карточка теперь одна на обе страницы, значит и данные ей нужны одинаковые. Лента их отдаёт, «Мои публикации» — нет: там не грузился автор (в карточке он появится как «Аноним») и не считался `is_liked` (сердечко всегда пустое, потому что `whenHas()` не отдаст ключ, которого нет у модели).

IN `app/Http/Controllers/Client/ProfileController.php`:
```php
        $posts = $profile->posts()
            // author добавился к category: карточка показывает ник автора,
            // и на своей странице он тоже должен быть виден. Это один
            // дополнительный запрос на всю страницу, а не на каждый пост.
            ->with(['author', 'category'])
            ->withCount('likedByProfiles')
            // Ровно тот же подзапрос, что в ленте. Профиль здесь точно есть —
            // выше стоит abort_if(), — поэтому whereKey() получит настоящий id.
            ->withExists([
                'likedByProfiles as is_liked' => fn (Builder $query) => $query->whereKey($profile->id),
            ])
            ->latest('id')
            ->paginate(10);
```

Плюс импорт `use Illuminate\Database\Eloquent\Builder;`.

Это типичное следствие переиспользования: компонент задаёт контракт данных, и все, кто его показывает, обязаны этот контракт выполнить. Выборки в двух контроллерах стали почти одинаковыми — но выносить общий скоуп по-прежнему рано: в ленте есть фильтр по статусу и своя сортировка, здесь их нет.

## 6. `ItemPost.vue` — карточка поста

Первый собственный компонент проекта. Всё, что он умеет, описывается двумя направлениями: данные приходят сверху пропсом (`post`), события уходят наверх (`deleted`). Внутрь него переезжает разметка карточки из обеих страниц и логика лайка из `Show.vue`.

IN `resources/js/Components/Post/ItemPost.vue`:
```vue
<template>
    <!--
        Один корневой элемент. Vue 3 разрешает несколько, но тогда «лишним»
        атрибутам (class со стороны родителя, слушателям) некуда приземлиться —
        Vue не угадает, какому корню они предназначены. Карточка — цельный блок,
        корень у неё естественным образом один.
    -->
    <article class="mb-4 rounded-lg bg-white p-5 shadow">
        <p class="mb-1 text-xs uppercase tracking-wider text-gray-400">
            {{ postData.author?.nickname ?? 'Аноним' }} ·
            {{ postData.category?.title ?? 'Без категории' }}
        </p>

        <Link
            :href="route('client.posts.show', postData.id)"
            class="text-lg font-semibold text-gray-900 hover:text-sky-700"
        >
            {{ postData.title }}
        </Link>

        <!--
            Бейдж переехал сюда со страницы «Мои публикации». В ленте условие
            не выполнится никогда — там только опубликованное, — и это нормально:
            карточка описывает пост, а не страницу, на которой её показывают.

            Сравнение с числом 1 — тот же шов между сервером и клиентом:
            константа Post::STATUS_PUBLISHED живёт в PHP.
        -->
        <span
            v-if="postData.status !== 1"
            class="ml-2 rounded bg-amber-100 px-2 py-0.5 text-xs text-amber-700"
        >
            На модерации
        </span>

        <p class="mt-2 whitespace-pre-line text-sm text-gray-700">
            {{ excerpt(postData.content) }}
        </p>

        <footer class="mt-3 flex items-center gap-4">
            <!--
                Кнопка лайка переехала со страницы поста почти без изменений.
                Заметьте, что isLikePending не мешает соседним карточкам: у каждого
                экземпляра компонента своё data(). В админском списке ради того же
                эффекта пришлось держать deletingId и сравнивать его с id строки —
                компонент снимает эту заботу.
            -->
            <button
                type="button"
                :disabled="isLikePending"
                :aria-pressed="postData.is_liked"
                class="inline-flex items-center gap-2 text-sm disabled:opacity-50"
                :class="postData.is_liked ? 'text-rose-600' : 'text-gray-400 hover:text-rose-500'"
                @click="toggleLike"
            >
                <svg
                    class="h-5 w-5"
                    viewBox="0 0 24 24"
                    :fill="postData.is_liked ? 'currentColor' : 'none'"
                    stroke="currentColor"
                    stroke-width="1.5"
                >
                    <path
                        stroke-linecap="round"
                        stroke-linejoin="round"
                        d="M21 8.25c0-2.485-2.099-4.5-4.688-4.5-1.935 0-3.597 1.126-4.312 2.733-.715-1.607-2.377-2.733-4.313-2.733C5.1 3.75 3 5.765 3 8.25c0 7.22 9 12 9 12s9-4.78 9-12Z"
                    />
                </svg>

                <span>{{ postData.likes_count }}</span>
            </button>

            <!--
                v-if по флагу с сервера, а не по сравнению id на клиенте (п. 4).

                class="ml-auto" на компоненте — не проп: Vue сам перенесёт его
                на корневой элемент DeletePost. Это fallthrough-атрибуты; так же
                пролетают style, id и обычные слушатели DOM-событий.

                @deleted — слушатель СВОЕГО события компонента, а не DOM-события.
                Такого события у браузера нет, его придумали мы (п. 7).
            -->
            <DeletePost
                v-if="postData.can_delete"
                :post="postData"
                class="ml-auto"
                @deleted="handleDeleted"
            />
        </footer>
    </article>
</template>

<script>
import axios from 'axios';
import { Link } from '@inertiajs/vue3';
import DeletePost from '@/Components/Post/DeletePost.vue';

export default {
    name: 'ItemPost',
    // Регистрация локальная, а не глобальная (app.component(...) в app.js):
    // компонент нужен только здесь, и по списку components видно, из чего
    // собран шаблон. Глобально регистрируют то, что встречается почти везде.
    components: { Link, DeletePost },
    // inject — обработчик, который положила страница через provide(). Разбор в п. 8.
    // Объектная форма нужна ради default: страница может его и не дать.
    inject: {
        onPostDeleted: { default: null },
    },
    props: {
        // Контракт компонента: он ждёт объект поста в том виде, в каком его отдаёт
        // PostResource — с author, category, likes_count, is_liked и can_delete.
        // required: true, потому что карточки без поста не бывает.
        post: {
            type: Object,
            required: true,
        },
    },
    data() {
        return {
            // Локальная копия пропса: лайк меняет is_liked и likes_count, а писать
            // в проп нельзя — поток данных односторонний. Копия поверхностная,
            // и этого достаточно: меняем только два скалярных поля.
            postData: { ...this.post },
            isLikePending: false,
        };
    },
    watch: {
        /**
         * Пересобирает локальную копию, когда с сервера приезжают свежие данные.
         *
         * data() выполняется один раз — при создании компонента. Карточка живёт
         * в v-for с :key="post.id", а router.reload() (п. 10) сохраняет состояние
         * страницы, поэтому уцелевшие карточки Vue переиспользует: экземпляр тот же,
         * data() второй раз не вызывается. Без наблюдателя в postData остались бы
         * счётчики, приехавшие при первой загрузке страницы.
         */
        post(value) {
            this.postData = { ...value };
        },
    },
    methods: {
        toggleLike() {
            this.isLikePending = true;

            axios
                .post(route('client.posts.likes.toggle', this.postData.id))
                .then((res) => {
                    // Оба значения берём из ответа, а не считаем на клиенте:
                    // пост могли лайкнуть другие, пока страница была открыта.
                    this.postData.is_liked = res.data.is_liked;
                    this.postData.likes_count = res.data.likes_count;
                })
                .catch((e) => {
                    console.log(e.response?.data);
                })
                .finally(() => {
                    this.isLikePending = false;
                });
        },
        /**
         * Реакция на событие от DeletePost.
         *
         * Карточка не решает, что делать дальше, — она передаёт факт странице.
         * Лента перезапросит список, страница поста сделала бы редирект (п. 8).
         *
         * ?. на случай, если страница не сделала provide(): вместо падения
         * просто ничего не произойдёт.
         */
        handleDeleted(postId) {
            this.onPostDeleted?.(postId);
        },
        excerpt(content, length = 200) {
            return content.length > length ? `${content.slice(0, length)}…` : content;
        },
    },
};
</script>
```

Обратите внимание, чего в компоненте нет: он не знает ни про ленту, ни про «Мои публикации», ни про пагинацию. Ему дали пост — он его нарисовал. Именно поэтому он переиспользуется, и по этому признаку («знает ли компонент, где его показывают») стоит проверять любой следующий.

## 7. `DeletePost.vue` — вложенный компонент и `emit`

Кнопку удаления можно было оставить прямо в `ItemPost`: это одна кнопка и один запрос. Вынесение оправдано двумя вещами. Во-первых, у кнопки есть собственное состояние (`isDeleting`) и собственный побочный эффект (`confirm` + запрос) — карточке они не нужны и только раздувают её. Во-вторых, та же кнопка понадобится на странице поста, где карточки нет вовсе.

IN `resources/js/Components/Post/DeletePost.vue`:
```vue
<template>
    <button
        type="button"
        :disabled="isDeleting"
        class="text-xs font-medium text-gray-400 hover:text-red-600 disabled:opacity-50"
        @click="destroyPost"
    >
        Удалить
    </button>
</template>

<script>
import axios from 'axios';

export default {
    name: 'DeletePost',
    props: {
        post: {
            type: Object,
            required: true,
        },
    },
    // Публичный контракт компонента наружу: «я умею сообщать о событии deleted».
    //
    // Объявлять не обязательно — $emit сработает и без этого списка, — но нужно
    // по двум причинам. Во-первых, это документация: по props и emits видно,
    // как компонентом пользоваться, не читая его код. Во-вторых, объявленные
    // события Vue исключает из fallthrough-атрибутов; без emits слушатель
    // onDeleted осел бы ещё и на корневом <button> как нативный обработчик
    // события deleted — оно никогда не произойдёт, но мусор в разметке останется.
    emits: ['deleted'],
    data() {
        return {
            isDeleting: false,
        };
    },
    methods: {
        destroyPost() {
            // Удаление необратимо, поэтому спрашиваем. confirm() — заглушка,
            // та же, что в админке: блокирует вкладку и выглядит по-разному
            // в разных браузерах, но честнее самодельной модалки, написанной с нуля.
            if (! confirm(`Удалить пост «${this.post.title}»?`)) {
                return;
            }

            this.isDeleting = true;

            axios
                .delete(route('client.posts.destroy', this.post.id))
                // Событие поднимаем ТОЛЬКО после успешного ответа: 403 или 500
                // означают, что пост на месте, и перезапрашивать список незачем.
                //
                // Второй аргумент $emit — полезная нагрузка события. У родителя
                // она приедет в $event или первым аргументом обработчика.
                .then(() => this.$emit('deleted', this.post.id))
                .catch((e) => {
                    console.log(e.response?.data);
                })
                .finally(() => {
                    this.isDeleting = false;
                });
        },
    },
};
</script>
```

Ключевая мысль про `emit`: компонент сообщает, ЧТО произошло, и не решает, что с этим делать. `DeletePost` знает, как удалить пост, и не знает, нужно ли после этого обновить список, показать уведомление или уйти на другую страницу. Если бы он звал `router.reload()` сам, он немедленно перестал бы годиться для страницы поста — там после удаления нужно уходить в ленту, а не перезагружать исчезнувший пост.

Стилевое замечание: компоненты Breeze (`Modal.vue`, `Checkbox.vue`) написаны в Composition API — там то же самое выглядит как `const emit = defineEmits(['close'])` и `emit('close')`. Проект пишет страницы в Options API, поэтому и свои компоненты держим в нём: смешивать два стиля в одной кодовой базе можно, но объяснять придётся оба.

## 8. Как не пробрасывать `emit` по уровням

Наивный вариант выглядит так — каждый промежуточный компонент пересылает чужое событие дальше:

```vue
<!-- ItemPost.vue: поймать и тут же переизлучить... -->
<DeletePost :post="postData" @deleted="$emit('deleted', $event)" />
```
```js
// ...и продублировать чужое событие в своём контракте
emits: ['deleted'],
```
```vue
<!-- Feed/Index.vue -->
<ItemPost :post="post" @deleted="reloadPosts" />
```

На двух уровнях это одна лишняя строка, и трагедии нет. Проблема в том, что строка не единственная и не последняя: каждый новый слой (обёртка `PostList.vue`, футер карточки отдельным компонентом) обязан объявить событие, поймать его и переслать — при том, что сам он про удаление ничего не знает и знать не хочет. Промежуточные компоненты начинают описывать чужие контракты.

Штатный ответ Vue на «дотянуться до предка через любое число уровней» — пара `provide`/`inject`. Предок кладёт значение в контекст, любой потомок ниже по дереву забирает его по ключу, промежуточные слои не участвуют вовсе.

IN `resources/js/Pages/Client/Feed/Index.vue`:
```js
    // provide — функцией, а не объектом: только так внутри доступен this.
    // Выполняется один раз при создании компонента, уже после methods и data,
    // поэтому ссылка на метод к этому моменту существует.
    //
    // Передаём функцию, а не данные: переданное через provide значение
    // не реактивно, и класть сюда что-то меняющееся было бы ошибкой.
    provide() {
        return {
            onPostDeleted: this.reloadPosts,
        };
    },
```

IN `resources/js/Components/Post/ItemPost.vue`:
```js
    // Объектная форма (а не inject: ['onPostDeleted']) нужна ради default:
    // без него Vue напишет в консоль «injection not found» и подставит undefined.
    // Значение по умолчанию делает компонент пригодным и там, где страница
    // ничего не предоставила.
    inject: {
        onPostDeleted: { default: null },
    },
```

Итоговая схема:

```
Feed/Index.vue            provide: onPostDeleted → reloadPosts()
  └── ItemPost.vue        inject: onPostDeleted; ловит @deleted и зовёт его
        └── DeletePost.vue    $emit('deleted', id)
```

`emit` работает там, где он естественен — между компонентом и его прямым родителем. `inject` перекрывает дистанцию до страницы, и сколько бы слоёв между ними ни появилось, менять их не придётся.

Цена решения — потерянная наглядность. Связь `@deleted="reloadPosts"` видна прямо в шаблоне страницы; `provide`/`inject` не виден нигде, кроме двух списков опций. Поэтому ключ называется говоряще (`onPostDeleted`, а не `handler`) — по нему `grep` находит обе стороны за один поиск.

Чем ещё это решают:

- **Fallthrough-атрибуты.** `inheritAttrs: false` в `ItemPost` плюс `v-bind="$attrs"` на `DeletePost` — и слушатель, повешенный на `<ItemPost>`, пролетает насквозь без единой строки пересылки. Коротко, но вместе со слушателем пролетит и всё остальное (`class`, `id`), а карточка потеряет управление своими атрибутами.
- **Шина событий** (`mitt` и подобные): глобальный объект, на который подписываются откуда угодно. Развязывает всё и одновременно ломает отладку — по коду больше не видно, кто кого слушает. Уместна для по-настоящему сквозных уведомлений (тостов), а не для «удалили пост».
- **Хранилище** (Pinia). Нужно, когда состояние общее для нескольких экранов. Здесь общего состояния нет, есть одно событие — заводить хранилище рано.
- **Не сообщать вообще**: `DeletePost` сам зовёт `router.reload()`. Самый короткий вариант и самый жёсткий — он приколачивает реакцию к кнопке. Ровно из-за этого переиспользовать её на странице поста уже не выйдет.

## 9. Страницы после переезда

`Feed/Index.vue` худеет до заголовка, списка карточек и пагинации.

IN `resources/js/Pages/Client/Feed/Index.vue`:
```vue

Обработчик тот же не случайно — на этой странице `posts.meta.total` выводится в шапке («Публикаций: N»), и после перезапроса он обновится сам.

## 10. `router.reload({ only: ['posts'] })` — частичная перезагрузка

После удаления список нужно обновить. Соблазн — выбросить пост из массива на клиенте; в 21-м уроке мы уже разобрали, почему так нельзя: `meta.total` останется прежним, кнопок пагинации будет на одну больше, чем нужно, а запись, которая должна была подняться со следующей страницы, на клиент просто не приезжала. Пересчитать это в браузере невозможно — `total` считает отдельный `count(*)`.

В админке ответом был повторный `axios.get()`. У Inertia для этого есть свой инструмент:

```js
router.reload({ only: ['posts'] });
```

Что происходит:

- **`reload()` — это `visit()` по текущему URL.** Адрес брать неоткуда и не нужно: `/feed?page=2` останется `/feed?page=2`, и пользователь после удаления окажется на той же странице списка.
- **`only: ['posts']` — частичная перезагрузка.** Inertia добавляет к запросу заголовок `X-Inertia-Partial-Data: posts`, и в ответ попадёт только этот проп. На странице профиля не поедет заново `profile`, на любой странице — общие `auth`.
- **Контроллер при этом выполняется целиком.** Заголовок отсекает пропсы на выходе, а не на входе: `ProfileResource::make($profile)` всё равно посчитается, просто результат выбросят. Чтобы не считать лишнего, проп оборачивают в замыкание (`'profile' => fn () => ...`) — Inertia вызовет его, только если проп действительно нужен. Ленивые пропсы в проекте пока не заводим, но знать про них стоит.
- **`preserveState` и `preserveScroll` у `reload()` включены по умолчанию.** Страница не пересоздаётся и не прыгает к началу — пользователь остаётся там, где кликнул. Оборотная сторона: экземпляры карточек живут дальше, и локальная копия пропса внутри них сама не обновится. Ради этого в `ItemPost` стоит наблюдатель за `post` (п. 6) — два решения связаны напрямую.

## 11. Тест на правило «удалять можно только своё»

Проверка авторства — то место, где тест окупается сразу: правило легко сломать невнимательной правкой, а руками проверять «а что видит чужой пользователь» долго.

```shell
php artisan make:test --phpunit ClientPostDestroyTest
```

IN `tests/Feature/ClientPostDestroyTest.php`:
```php
<?php

namespace Tests\Feature;

use App\Models\Post;
use App\Models\Profile;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class ClientPostDestroyTest extends TestCase {
    use RefreshDatabase;

    public function test_author_deletes_own_post(): void {
        $profile = Profile::factory()->create();
        // for($profile, 'author') — связь называется author, а не profile,
        // поэтому имя приходится указывать явно.
        $post = Post::factory()->for($profile, 'author')->create();

        // actingAs принимает пользователя, а не профиль: аутентификация в Laravel
        // работает с User, профиль — уже наша предметная область.
        $response = $this->actingAs($profile->user)
            ->deleteJson(route('client.posts.destroy', $post));

        $response->assertNoContent();
        $this->assertDatabaseMissing('posts', ['id' => $post->id]);
    }

    public function test_stranger_cannot_delete_foreign_post(): void {
        $post = Post::factory()->create();
        $stranger = Profile::factory()->create();

        $response = $this->actingAs($stranger->user)
            ->deleteJson(route('client.posts.destroy', $post));

        $response->assertForbidden();
        // Проверяем не только код ответа, но и базу: 403 без этой строки
        // мог бы прийти уже ПОСЛЕ удаления.
        $this->assertDatabaseHas('posts', ['id' => $post->id]);
    }
}
```

`deleteJson`, а не `delete`: так запрос уходит с `Accept: application/json`, и при неудаче в отчёте будет видно тело ответа, а не HTML страницы ошибки.

## 13. Грабли

- **`Failed to resolve component: ItemPost`** — компонент не зарегистрирован в `components` страницы либо путь в `import` не совпал с именем файла. Путь чувствителен к регистру, `@` — алиас на `resources/js` от `laravel-vite-plugin`.
- **Кнопки удаления нет ни у одного поста** — забыли `can_delete` в `PostResource`: в шаблоне это `undefined`, и `v-if` ложен.
- **Кнопка есть у чужих постов** — сравнили `author_id` с `user.id` вместо `profile.id`. Это разные таблицы, и совпадение id — случайность.
- **403 при удалении своего поста** — у пользователя нет профиля (`?->` даёт `null`) либо пост создан от другого профиля.
- **405 Method Not Allowed** — `axios.post()` вместо `axios.delete()`. `route()` отдаёт только URL, про метод Ziggy ничего не знает.
- **Карточка исчезла, а «Всего» осталось прежним** — вместо `router.reload()` пост удалён из массива на клиенте.
- **Счётчики лайков не обновляются после перезагрузки списка** — нет наблюдателя за пропом `post` в `ItemPost`: `data()` при переиспользовании экземпляра второй раз не выполняется.
- **После удаления ничего не происходит, ошибок нет** — страница не сделала `provide()`, а в `ItemPost` стоит `default: null` и `?.()`. Молчаливое поведение — плата за необязательный inject; ищите по имени ключа.
- **В консоли `injection "onPostDeleted" not found`** — `inject` объявлен массивом вместо объектной формы с `default`.
- **`Avoid mutating a prop directly`** — лайк пишет в `post`, а не в `postData`.
- **Событие `deleted` не долетает** — слушатель повешен не на компонент или имя не совпало: `@deleted` ловит только `$emit('deleted')`, регистр и дефисы значимы.
- **На странице «Мои публикации» все сердечки пустые** — в `ProfileController` не добавлен `withExists()`, ключа `is_liked` в ответе нет.
- **Автор в карточке «Аноним» на своей же странице** — там же не добавлен `with('author')`.
- **Пустой список после удаления последней записи на не первой странице** — `reload()` идёт по тому же URL с `?page=3`, а такой страницы уже нет, и пагинатор честно возвращает пустой массив. Лечение — в п. 14.
- **Белая страница, ошибка Vite в консоли** — новые `.vue`-файлы появились после старта дев-сервера, `composer run dev` нужно перезапустить.

## 14. Что можно сделать лучше

**`PostPolicy` вместо `abort_unless()` и ручного сравнения.** Правило «удалять можно своё» сейчас записано дважды: в контроллере и в ресурсе. Политика убирает дублирование: в контроллере останется `Gate::authorize('delete', $post)`, в ресурсе — `'can_delete' => $request->user()?->can('delete', $this->resource)`, а само правило будет лежать в одном методе. Заодно закроется дыра в админке, где удалить может любой залогиненный.

**`DeletePost` на странице поста.** Три строки в `Show.vue` — и кнопка появляется там же; `provide()` этой страницы вернёт не перезагрузку, а `() => router.visit(route('client.feed.index'))`. Это лучшая иллюстрация того, зачем компоненту `emit`: код кнопки не меняется вообще, меняется только реакция страницы.

**`LikePost.vue` рядом с `DeletePost.vue`.** Логика лайка сейчас написана дважды — в `ItemPost` и в `Show.vue`. Вынесенная в компонент, она уберёт дублирование ровно так же, как это сделала кнопка удаления.

**`Pagination.vue`.** Блок `<nav>` с кнопками страниц одинаков в `Feed/Index.vue` и `Profile/Personal.vue` до последнего класса. Следующий очевидный кандидат на компонент — и заодно повод разобрать слоты.

**Возврат на предыдущую страницу.** Если удалена последняя запись на странице, стоит уйти на предыдущую: `router.get(route('client.feed.index'), { page: currentPage - 1 })`. Условие то же, что в админке 21-го урока: «на экране была ровно одна карточка, и страница не первая».

**Модальное окно вместо `confirm()`.** У Breeze уже есть `Components/Modal.vue`; заодно это упражнение на слоты и на события (`@close`).

**Мягкое удаление.** Трейт `SoftDeletes` и колонка `deleted_at` дали бы возможность восстановить пост и не терять комментарии. Сейчас `PostService::destroy()` сносит всё окончательно.

**Оптимистичное обновление лайка.** Перекрашивать сердечко сразу, а в `.catch()` откатывать. Взамен придётся помнить предыдущее состояние.

**Ленивые пропсы.** `'profile' => fn () => ProfileResource::make($profile)->resolve()` в `ProfileController` — и при частичной перезагрузке `only: ['posts']` профиль не будет пересчитываться впустую.
