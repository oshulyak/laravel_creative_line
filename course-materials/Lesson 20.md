# Lesson 20 - Pagination

Цель урока: заменить `->get()` в списке постов на `->paginate()`, отдать клиенту постраничный ответ через API Resource и нарисовать переключатель страниц, который уживается с фильтром из 19-го урока.

По пути разбираются: `LengthAwarePaginator` и SQL, который он строит; форма ответа `data` / `links` / `meta` у ресурсной коллекции; почему из контроллера исчезает `->resolve()`; `prepareForValidation()` как место для значений по умолчанию; вложенные ключи в правилах (`filters.title`, `pagination.page`); `meta.links` и `v-html`; сброс на первую страницу при смене фильтра.

Отправная точка — состояние после 19-го урока: `PostController::index()` отдаёт либо Inertia-страницу, либо JSON-массив постов; `Index.vue` держит `filter` в `data()`, следит за ним через `watch` с debounce и заменяет `postsData`.

## 1. `get()` → `paginate()`: что меняется в SQL

`->get()` тянет все строки, подошедшие под условия. Пока постов десяток — незаметно; на тысяче это лишний трафик, лишняя память PHP и лишняя работа Vue, который отрисует тысячу `<tr>`.

`->paginate()` решает ту же задачу двумя запросами вместо одного:

```sql
-- 1. Сколько всего строк подошло под фильтр (нужно, чтобы знать число страниц)
select count(*) as aggregate from "posts" where lower("title") like lower('%laravel%');

-- 2. Только нужный кусок, в стабильном порядке
select * from "posts"
where lower("title") like lower('%laravel%')
order by "id" desc
limit 5 offset 10;
```

Что здесь изучается:

- **`limit` + `offset`.** Номер страницы превращается в смещение по формуле `offset = ($page - 1) * $perPage`. Третья страница по 5 записей — это `limit 5 offset 10`.
- **Второй запрос — `count(*)`.** Он и есть цена «умной» пагинации: без него нельзя показать «страница 3 из 12». Если общее число страниц не нужно, есть `simplePaginate()` — он делает только один запрос (см. п.12).
- **Возвращается не коллекция, а `Illuminate\Pagination\LengthAwarePaginator`.** Это объект, который умеет и то, что умеет коллекция (по нему можно итерироваться), и знает про себя `currentPage()`, `lastPage()`, `total()`, `perPage()`, `hasMorePages()`.
- **Сортировка становится обязательной.** `latest('id')` в `index()` стоял ещё с 15-го урока, и теперь его нельзя убирать ни при каких условиях. Без `order by` PostgreSQL не обещает порядок строк вообще: одна и та же запись может приехать и на первой странице, и на второй, а какая-то — не приехать вовсе. Это не теоретическая придирка, а прямое следствие того, как работает `offset`.
- **`$perPage` по умолчанию — 15.** `->paginate()` без аргументов берёт значение из свойства `$perPage` модели (`Illuminate\Database\Eloquent\Model::$perPage = 15`). Его можно переопределить в `Post`, но в этом уроке число приезжает с клиента.
- **Маленькая оптимизация внутри.** Если `count(*)` вернул ноль, второй запрос Laravel даже не выполняет — сразу отдаёт пустую коллекцию.

## 2. Форма ответа: `data`, `links`, `meta`

Пагинатор сам по себе — объект PHP. Чтобы он превратился в JSON правильной формы, его нужно **отдать в ресурсную коллекцию**:

```php
PostResource::collection($paginator)
```

`ResourceCollection::toResponse()` видит, что внутри лежит пагинатор, и вместо обычного `ResourceResponse` берёт `PaginatedResourceResponse`. Ответ получается такой:

```json
{
    "data": [
        { "id": 42, "title": "…", "likes_count": 3, "category": { "id": 1, "title": "…" } }
    ],
    "links": {
        "first": "http://line.test/admin/posts?page=1",
        "last":  "http://line.test/admin/posts?page=3",
        "prev":  null,
        "next":  "http://line.test/admin/posts?page=2"
    },
    "meta": {
        "current_page": 1,
        "from": 1,
        "last_page": 3,
        "links": [
            { "url": null, "label": "&laquo; Previous", "page": null, "active": false },
            { "url": "http://line.test/admin/posts?page=1", "label": "1", "page": 1, "active": true },
            { "url": "http://line.test/admin/posts?page=2", "label": "2", "page": 2, "active": false },
            { "url": "http://line.test/admin/posts?page=2", "label": "Next &raquo;", "page": 2, "active": false }
        ],
        "path": "http://line.test/admin/posts",
        "per_page": 5,
        "to": 5,
        "total": 13
    }
}
```

Что здесь изучается:

- **Два разных `links`.** Верхний — четыре именованные ссылки (`first`, `last`, `prev`, `next`), удобные для кнопок «в начало / назад / вперёд». Вложенный `meta.links` — готовый массив для нумерованного переключателя: по элементу на каждую кнопку, включая «Previous», «Next» и разделитель `...`. Рисовать мы будем именно по `meta.links`.
- **Обёртка `data` появляется всегда.** Даже если у ресурса отключить `wrap`, у постраничного ответа обёртка останется: иначе некуда положить `meta` и `links`. Это прямо оговорено в документации.
- **`label` содержит HTML-сущности.** `&laquo; Previous` и `Next &raquo;` берутся из языкового файла `vendor/laravel/framework/src/Illuminate/Translation/lang/en/pagination.php`. Отсюда `v-html` в шаблоне (п.8): через `{{ }}` пользователь увидел бы буквально `&laquo; Previous`.
- **`page` в каждом элементе `meta.links`** — номер страницы числом. Это ключевая мелочь урока: по нему кнопка ставит новую страницу, не разбирая строку `label`. У неактивных стрелок («Previous» на первой странице, «Next» на последней) `page` и `url` равны `null`. У разделителя `...` ключа `page` нет вообще: `LengthAwarePaginator::linkCollection()` собирает его отдельной веткой из трёх ключей — `['url' => null, 'label' => '...', 'active' => false]`. На клиенте это `undefined`, а не `null`, — на код кнопки не влияет (кликать по разделителю всё равно нельзя из-за `url === null`), но знать разницу полезно.
- **`resolve()` больше не нужен — и вреден.** В 15–19 уроках мы писали `PostResource::collection($posts)->resolve()`, чтобы Inertia не завернула данные в лишний `data`. `resolve()` возвращает **только массив элементов**, поэтому `meta` и `links` он выбросит. Теперь обёртка `data` — не помеха, а часть контракта, и `resolve()` нужно убрать.
- **Inertia отдаёт ту же самую форму.** В `Inertia\Response::resolvePropertyInstances()` есть ветка: если проп — `Responsable`, вызывается `toResponse($request)->getData(true)`. `AnonymousResourceCollection` реализует `Responsable`, значит проп `posts` на клиенте будет тем же объектом `{ data, links, meta }`, что и ответ axios. Благодаря этому строка `postsData: this.posts` в `data()` продолжает работать без единой правки.

## 3. Первый шаг: жёстко зашитые параметры и `dd()`

Прежде чем тянуть параметры с клиента, полезно один раз посмотреть, что вообще возвращает пагинатор.

IN `app/Http/Controllers/Admin/PostController.php`:
```php
$data = $request->validated();

// 5 — записей на странице, ['*'] — какие колонки выбрать,
// 'page' — имя query-параметра, 1 — номер страницы.
$posts = PostResource::collection(Post::filter($data)->paginate(5, ['*'], 'page', 1));

dd($posts);
```

Что здесь изучается:

- **Сигнатура `paginate($perPage, $columns, $pageName, $page)`.** Первый и последний аргументы — то, ради чего всё затевается; средние два нужны редко.
- **`$columns` — массив.** В видео написано `'*'` строкой, и это работает: внутри `Builder::get()` стоит `Arr::wrap($columns)`. Но конвенция — `['*']`, и в проекте лучше писать так: сигнатура метода и PHPDoc обещают массив.
- **`$pageName` — имя query-параметра.** Он нужен, когда на одной странице два независимых списка: тогда второму дают `'posts_page'`, чтобы номера страниц не путались. У нас список один, `'page'` — значение по умолчанию.
- **Четвёртый аргумент `$page` можно не передавать.** Если его нет, Laravel сам вытащит номер страницы из запроса через `Paginator::resolveCurrentPage()` — резолвер зарегистрирован в `PaginationState` и читает `request()->input('page')`. То есть при обычном контракте `?page=2` весь код сводится к `->paginate(5)`. Мы передаём номер явно, потому что дальше (п.9) параметр переедет в `pagination[page]`, а туда резолвер не смотрит.
- **Мусорный `$page` до базы не доедет — но и ошибки не будет.** Резолвер попутно проверяет значение: `filter_var(..., FILTER_VALIDATE_INT)` и `>= 1`, иначе возвращает 1. Передавая номер явно, мы этот резолвер обходим, но не остаёмся без защиты — её ставит сам фреймворк, в трёх местах:

  1. `Builder::paginate()` начинается со строки `$page = $page ?: Paginator::resolveCurrentPage($pageName);`. Оператор `?:`, а не `??`, поэтому `0` (как и `null`, и `''`) считается пустым и всё-таки уходит в резолвер.
  2. `Query\Builder::offset()` пишет `$this->offset = max(0, (int) $value)`. Отрицательное смещение обрезается до нуля, и `OFFSET` в SQL никогда не бывает отрицательным.
  3. `LengthAwarePaginator::setCurrentPage()` прогоняет номер через `isValidPageNumber()` и подменяет невалидный на 1.

  Проверяется одной строкой: `Post::query()->latest('id')->paginate(5, ['*'], 'page', -3)` возвращает `current_page = 1` и выполняет `... limit 5 offset 0`. Никакого `SQLSTATE`.

  Правило `min:1` в реквесте (п.4) всё равно нужно — но не как защита от падения, а как честный контракт: на `pagination[page]=0` сервер отвечает 422 «так нельзя», вместо того чтобы молча отдать первую страницу. Молчаливая подмена хуже: клиент останется в уверенности, что показывает нулевую страницу, и подсветка кнопок разъедется с содержимым таблицы.
- **`dd()` как способ увидеть форму данных.** В дампе видно и `LengthAwarePaginator` внутри, и `total`, и `perPage`. После просмотра `dd()` убираем — это отладочный костыль, а не часть кода.

## 4. `page` и `per_page` в `IndexRequest`

Числа 5 и 1 в контроллере — заглушки. Настоящие значения приходят с клиента, значит проходят через тот же реквест, что и фильтр.

IN `app/Http/Requests/Admin/Post/IndexRequest.php`:
```php
public function rules(): array {
    return [
        'title' => ['nullable', 'string', 'max:255'],
        'published_at_from' => ['nullable', 'date_format:Y-m-d'],
        'likes_from' => ['nullable', 'integer', 'min:0'],
        'page' => ['nullable', 'integer', 'min:1'],
        'per_page' => ['nullable', 'integer', 'min:1', 'max:100'],
    ];
}

/**
 * Значения по умолчанию для пагинации.
 *
 * Хук вызывается до запуска валидатора, поэтому merge() дописывает ключи
 * в данные запроса, и правила проверяют уже дополненный набор.
 */
protected function prepareForValidation(): void {
    $this->merge([
        'page' => $this->input('page', 1),
        'per_page' => $this->input('per_page', 5),
    ]);
}
```

Что здесь изучается:

- **`prepareForValidation()` — штатная точка расширения `FormRequest`.** Он вызывается из `ValidatesWhenResolvedTrait::validateResolved()` **до** `rules()`. Внутри можно нормализовать вход: подставить значения по умолчанию, привести формат, переименовать ключ.
- **Почему значения по умолчанию именно здесь, а не в контроллере.** Альтернатива — `$data['per_page'] ?? 5` в `index()`. Работает, но тогда «сколько записей на странице по умолчанию» становится знанием контроллера, а контракт запроса — неполным. В реквесте после `validated()` ключи гарантированно есть, и контроллер читает их без `??`.
- **`$this->input('page', 1)`, а не `$this->page ?? 1`.** Магическое свойство `$this->page` тоже читает вход, но у `input()` есть второй аргумент — значение по умолчанию, и он умеет точечную нотацию (`input('pagination.page')`), которая понадобится в п.9. Разница видна на краю: если пришло `page=0`, `??` его пропустит (это не `null`), а валидация всё равно отсеет по `min:1` — то есть подмена значения по умолчанию и проверка диапазона остаются разными шагами, и это правильно.
- **`max:100` у `per_page`.** Значение приезжает от клиента, а клиенту верить нельзя: `?per_page=1000000` — это запрос всей таблицы одним куском, то есть бесплатный способ положить приложение. Верхняя граница обязательна везде, где размер страницы задаёт пользователь.
- **`min:1` у `page`.** Не защита от падения — падать там нечему (п.3), а явный контракт: невалидный номер страницы должен возвращаться клиенту как 422, а не подменяться первой страницей за его спиной.
- **`nullable`, а не `required`.** Первый заход на страницу может не прислать ничего, и это норма: значения подставит `prepareForValidation()`.

## 5. Контроллер: параметры пагинации из запроса

IN `app/Http/Controllers/Admin/PostController.php`:
```php
public function index(IndexRequest $request): AnonymousResourceCollection|Response {
    $data = $request->validated();

    $posts = Post::query()
        ->filter($data)
        ->with('category')
        ->withCount('likedByProfiles')
        ->latest('id')
        ->paginate($data['per_page'], ['*'], 'page', $data['page']);

    $posts = PostResource::collection($posts);

    return $request->wantsJson() ? $posts : inertia('Admin/Post/Index', compact('posts'));
}
```

Что здесь изучается:

- **`filter($data)` не мешает пагинации.** В `$data` теперь лежат и `page`, и `per_page`, но `AbstractFilter::apply()` ходит только по своему белому списку `$keys`, а этих ключей там нет. Лишние ключи фильтр молча игнорирует — ровно то поведение, ради которого белый список и заводили в 13-м уроке.
- **`paginate()` идёт последним.** Это не стилистика: `paginate()` **выполняет** запрос и возвращает пагинатор, а не билдер. Всё, что должно попасть в SQL, обязано быть вызвано до него.
- **`withCount()` и `paginate()` дружат.** Считая `count(*)` для пагинации, Laravel клонирует запрос без колонок (`cloneWithout(['columns', 'orders', 'limit', 'offset'])`), поэтому подзапрос-счётчик лайков в подсчёт строк не попадает и лишней работы не делает.
- **Тип возврата сменился с `array` на `AnonymousResourceCollection`.** Раньше `index()` возвращал массив, потому что `->resolve()` разворачивал ресурс в массив. Теперь возвращается сам объект коллекции: он реализует `Responsable`, и Laravel сам превратит его в `JsonResponse` со структурой `data/links/meta`. Не забыть импорт:

  ```php
  use Illuminate\Http\Resources\Json\AnonymousResourceCollection;
  ```
- **Обе ветки отдают одинаковую структуру.** JSON-ветка — через `Responsable` в роутере, Inertia-ветка — через `resolvePropertyInstances()` (п.2). Это и позволяет клиенту не различать, откуда приехали данные.
- **`with('category')` по-прежнему обязателен.** Пагинация уменьшает число строк, но N+1 никуда не девается: без eager loading пять строк дадут пять дополнительных запросов вместо тысячи. Меньше — не значит «можно».

## 6. `Index.vue`: `postsData.data` вместо `postsData`

Форма данных изменилась, значит все места, где компонент считал `postsData` массивом, надо поправить. Их три.

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<span class="text-sm text-gray-500">Всего: {{ postsData.meta.total }}</span>
```

```vue
<tr
    v-for="post in postsData.data"
    :key="post.id"
    class="align-top transition-colors hover:bg-gray-50"
>
```

```vue
<tr v-if="!postsData.data.length">
    <td colspan="8" class="px-4 py-10 text-center text-gray-500">
        Публикаций пока нет.
    </td>
</tr>
```

И тип пропса:

```js
props: {
    posts: {
        type: Object,
        // Заглушка обязана иметь ту же форму, что настоящий ответ:
        // шаблон обращается к postsData.meta.links ещё до первого запроса.
        default: () => ({ data: [], meta: { links: [], total: 0 } }),
    },
},
```

Что здесь изучается:

- **`Всего` теперь означает другое.** `postsData.length` показывал длину массива — то есть число загруженных постов. `meta.total` — число постов, подошедших под фильтр, независимо от страницы. Это и есть правильный смысл слова «всего»; заодно видно, зачем пагинатор делает второй запрос `count(*)`.
- **`type: Object` вместо `type: Array`.** Vue проверяет тип пропса в dev-сборке и напишет в консоль `Invalid prop: type check failed`. Предупреждение не ломает страницу, поэтому его легко пропустить — но чинить надо, а не терпеть.
- **`default` с полной формой объекта.** Значение по умолчанию у объектов и массивов задаётся фабрикой (`() => ({...})`), иначе все экземпляры компонента делили бы один объект. Важно, что заглушка содержит `meta.links`: иначе на любом маршруте, где проп не пришёл, шаблон упадёт с `Cannot read properties of undefined`.

## 7. Переключатель страниц

IN `resources/js/Pages/Admin/Post/Index.vue`, сразу после блока с таблицей:
```vue
<!--
    Кнопки страниц строим по meta.links — Laravel уже посчитал,
    какие номера показать, какой активен и где поставить «...».
-->
<nav v-if="postsData.meta.last_page > 1" class="mt-4 flex flex-wrap gap-1">
    <button
        v-for="(link, index) in postsData.meta.links"
        :key="index"
        type="button"
        :disabled="!link.url || link.active"
        class="border px-3 py-2 text-sm disabled:cursor-default disabled:text-gray-300"
        :class="link.active
            ? 'border-sky-800 bg-sky-700 text-white'
            : 'border-gray-300 bg-white hover:bg-gray-50'"
        @click="entries.pagination.page = link.page"
        v-html="link.label"
    ></button>
</nav>
```

Что здесь изучается:

- **`v-html`, а не `{{ }}`.** В `label` лежат HTML-сущности `&laquo;` и `&raquo;`. Интерполяция экранирует текст и покажет их буквально; `v-html` вставляет разметку как есть. Общее правило: `v-html` опасен, потому что вставляет чужой HTML без экранирования (XSS). Здесь это допустимо, потому что источник строки — языковой файл фреймворка, а не пользовательский ввод. Как только в `label` начнёт попадать что-то от пользователя, `v-html` придётся убирать.
- **`link.page`, а не `link.label`.** В видео стоит `@click="this.filter.page = link.label"`, и это работает ровно до первого клика по «Previous»: в `page` уедет строка `&laquo; Previous`, реквест ответит 422. Разбирать `label` регуляркой или вытаскивать номер из `link.url` не нужно — в каждом элементе `meta.links` есть готовое числовое поле `page`. Проверить состав элемента можно прямо в исходниках фреймворка: `LengthAwarePaginator::linkCollection()`.
- **`:disabled="!link.url || link.active"`.** У разделителя `...` и у неактивных «Previous»/«Next» `url` равен `null` — кликать по ним нечего. Активную страницу тоже блокируем: перезапрашивать то, что уже на экране, незачем.
- **`:key="index"`, а не `link.page`.** Обычно ключом берут стабильный идентификатор, но здесь его нет: у неактивных стрелок `page` равен `null`, у разделителя `...` ключа `page` нет вовсе (п.2), — то есть у нескольких элементов ключ оказался бы одинаково пустым. Индекс допустим, потому что список статичен по структуре: он не сортируется и не фильтруется, а перерисовывается целиком.
- **`<button>`, а не `<div>`.** В видео кнопки нарисованы через `<div class="cursor-pointer">`. Визуально то же самое, но `<button>` фокусируется с клавиатуры, срабатывает по Enter и Space, объявляется скринридером как кнопка и умеет `disabled`. `type="button"` — чтобы кнопка не сабмитила форму, если её когда-нибудь обернут в `<form>`.
- **`v-if="last_page > 1"`.** Одна страница — переключатель не нужен. Laravel в этом случае всё равно вернёт три элемента в `meta.links` («Previous», «1», «Next»), так что без проверки на экране висел бы бессмысленный блок.

## 8. Сброс на первую страницу

Тонкость, которую видно только в работе: пользователь листает до третьей страницы, потом что-то печатает в фильтре — и получает пустой список, потому что под новый фильтр подошло 4 поста, а мы просим третью страницу.

Логика простая: **любое изменение фильтра сбрасывает страницу на первую**. Изменение самой страницы — нет.

Отсюда два отдельных наблюдателя вместо одного (реализация — в п.10):

```js
watch: {
    'entries.filters': {
        handler() {
            this.entries.pagination.page = 1;
            this.scheduleFilterPosts();
        },
        deep: true,
    },
    'entries.pagination': {
        handler() {
            this.scheduleFilterPosts();
        },
        deep: true,
    },
},
```

Что здесь изучается:

- **Строка как имя наблюдаемого.** `watch` умеет следить не только за корневым ключом, но и за путём: `'entries.filters'` — валидное имя. Это избавляет от промежуточных `computed`.
- **`deep: true` нужен обоим.** Причина та же, что в 19-м уроке: меняется свойство внутри объекта, а ссылка на сам объект остаётся прежней.
- **Почему нельзя обойтись одним наблюдателем за `entries`.** Он не различает, что именно изменилось, и сбрасывал бы `page = 1` в том числе при клике по кнопке «2» — то есть переключатель страниц перестал бы работать вообще.
- **Ловушка двойного запроса.** Когда `page` действительно меняется (пользователь был на третьей странице), присваивание внутри первого наблюдателя разбудит второй, и `filterPosts()` окажется вызван дважды. Лечится тем, что оба наблюдателя зовут не сам запрос, а **один общий отложенный вызов**: второй `clearTimeout` отменяет первый таймер, и в сеть уходит один запрос. Если бы наблюдатели дёргали `filterPosts()` напрямую (как в видео), запросов было бы два.
- **Когда `page` уже равен 1, второй наблюдатель молчит.** Vue сравнивает значения и не запускает обработчик, если ничего не изменилось. То есть обычный случай «фильтрую, находясь на первой странице» лишних срабатываний не даёт.

## 9. Рефакторинг: `filters` и `pagination` — два блока

Пока параметров было три, плоский список читался нормально. Теперь их пять, и они разной природы: три описывают **что выбрать**, два — **как нарезать**. В видео контракт переделывается во вложенный:

```
?filters[title]=laravel&filters[likes_from]=3&pagination[page]=2&pagination[per_page]=5
```

IN `app/Http/Requests/Admin/Post/IndexRequest.php`:
```php
/**
 * Query-параметры админского списка постов, сгруппированные в два блока:
 * filters — условия отбора, pagination — нарезка на страницы.
 *
 * Точка в имени ключа — обращение к вложенному значению: правило filters.title
 * проверяет $data['filters']['title'].
 *
 * @return array<string, ValidationRule|array<mixed>|string>
 */
public function rules(): array {
    return [
        'filters' => ['nullable', 'array'],
        'filters.title' => ['nullable', 'string', 'max:255'],
        'filters.published_at_from' => ['nullable', 'date_format:Y-m-d'],
        'filters.likes_from' => ['nullable', 'integer', 'min:0'],

        'pagination' => ['nullable', 'array'],
        'pagination.page' => ['nullable', 'integer', 'min:1'],
        'pagination.per_page' => ['nullable', 'integer', 'min:1', 'max:100'],
    ];
}

/**
 * Значения по умолчанию для пагинации.
 */
protected function prepareForValidation(): void {
    $this->merge([
        'filters' => $this->input('filters', []),
        'pagination' => [
            'page' => $this->input('pagination.page', 1),
            'per_page' => $this->input('pagination.per_page', 5),
        ],
    ]);
}
```

IN `app/Http/Controllers/Admin/PostController.php`:
```php
$data = $request->validated();

$posts = Post::query()
    // ?? [] — обязательно, объяснение ниже.
    ->filter($data['filters'] ?? [])
    ->with('category')
    ->withCount('likedByProfiles')
    ->latest('id')
    ->paginate($data['pagination']['per_page'], ['*'], 'page', $data['pagination']['page']);
```

Что здесь изучается:

- **Точечная нотация в правилах.** `filters.title` — это путь к вложенному значению, тот же синтаксис, что у `Arr::get()` и у `$request->input()`. Так же валидируются массивы: `images.*.file` из 15-го урока — родственная конструкция.
- **Правило на контейнер проверяет тип, но не гарантирует ключ.** Строки `'filters' => ['nullable', 'array']` и `'pagination' => ['nullable', 'array']` нужны: без них `?filters=строка` доехал бы до фильтра. А вот присутствия блока в `validated()` они, вопреки интуиции, **не** обеспечивают — наоборот, отбирают его.

  Виноват флаг `excludeUnvalidatedArrayKeys`, включённый в `Illuminate\Validation\Factory` (`protected $excludeUnvalidatedArrayKeys = true;`) и поэтому действующий на все `FormRequest`. В `Validator::validated()` из-за него стоит такая ветка:

  ```php
  foreach ($this->getRules() as $key => $rules) {
      $value = data_get($this->getData(), $key, $missingValue);

      if ($this->excludeUnvalidatedArrayKeys &&
          (in_array('array', $rules) || in_array('list', $rules)) &&
          $value !== null &&
          ! empty(preg_grep('/^'.preg_quote($key, '/').'\.+/', array_keys($this->getRules())))) {
          continue;   // ← контейнер пропущен целиком
      }

      if ($value !== $missingValue) {
          Arr::set($results, $key, $value);
      }
  }
  ```

  Смысл флага — не пускать наружу непроверенные подключи: раз для `filters` объявлены вложенные правила, сам `filters` в результат не копируется, а собирается заново из тех `filters.*`, которые реально пришли. Поведение ровно обратное ожидаемому: **чем подробнее описан контейнер, тем меньше шансов увидеть его в `validated()`**.

  Отсюда разное поведение двух блоков:

  ```
  пустая форма: {"pagination":{"page":1,"per_page":5}}
  с фильтром:   {"filters":{"title":"laravel"},"pagination":{"page":2,"per_page":10}}
  ```

  `pagination` выживает не благодаря правилу на контейнер, а благодаря `prepareForValidation()`: оба вложенных ключа есть всегда, значит блоку есть из чего собраться. У `filters` значений по умолчанию нет и быть не должно — на пустой форме вложенных ключей ноль, собирать нечего, и ключа `filters` в `validated()` не будет. Поэтому в контроллере `$data['filters'] ?? []`, иначе первый же заход на `/admin/posts` даёт `ErrorException: Undefined array key "filters"`.

  Альтернатива, если `??` в контроллере не нравится, — читать блок через `$request->validated('filters', [])`: у `FormRequest::validated()` есть второй аргумент «значение по умолчанию», и он делает то же самое, но оставляет знание о контракте в реквесте.
- **`prepareForValidation()` пишет `pagination` целиком.** Записать `$this->merge(['page' => ...])` (как в видео) не получится: это добавит ключ верхнего уровня, а правила смотрят в `pagination.page`. Значение по умолчанию должно лечь ровно туда, где его ищет валидатор.
- **`$this->input('pagination.page', 1)` вместо `$this->pagination['page'] ?? 1`.** Когда блока `pagination` в запросе нет, `$this->pagination` равно `null`, и обращение `null['page']` даёт PHP-warning `Trying to access array offset on value of type null`. Ошибки не будет, страница отработает, но в логах появится мусор. `input()` с точечной нотацией такой ситуации не создаёт.
- **`PostFilter` не изменился ни на строку.** Фильтр по-прежнему получает плоский массив `['title' => ..., 'likes_from' => ...]` — контроллер просто достаёт его из `$data['filters']`. Группировка — это про контракт HTTP, а не про фильтр: наглядное разделение ответственности.
- **Стоит ли так делать.** Плоский контракт короче, а `?page=2` — общепринятая конвенция, под которую Laravel умеет подставлять номер страницы сам. Вложенный контракт даёт другое: границы блоков видно в URL, добавление шестого фильтра не размывает список параметров, и на клиенте `params` собирается одним объектом. Для админки с растущим числом фильтров это оправданный обмен; для публичного API лучше плоский `?page=`, потому что его ждут все клиенты.

## 10. `entries`: итоговый `<script>` в `Index.vue`

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<script>
import axios from 'axios';
import { Head, Link } from '@inertiajs/vue3';
import AdminLayout from '@/Layouts/AdminLayout.vue';

export default {
    name: 'Index',
    layout: AdminLayout,
    components: { Head, Link },
    props: {
        posts: {
            type: Object,
            default: () => ({ data: [], meta: { links: [], total: 0 } }),
        },
    },
    data() {
        return {
            // Структура повторяет контракт IndexRequest: два блока, snake_case внутри.
            // Весь объект целиком уезжает в params, поэтому имена ключей должны
            // совпадать с правилами валидации и с $keys у PostFilter.
            entries: {
                // filters, а не filter: имя обязано совпадать с правилом из IndexRequest.
                filters: {
                    title: '',
                    published_at_from: '',
                    likes_from: null,
                },
                pagination: {
                    page: 1,
                    per_page: 5,
                },
            },
            // Ответ сервера целиком: { data, links, meta }. Сначала — то, что приехало
            // пропсом, потом — то, что вернул axios. Форма у них одинаковая.
            postsData: this.posts,
            timerId: null,
        };
    },
    watch: {
        'entries.filters': {
            handler() {
                // Новый фильтр — снова с первой страницы: на третьей может уже
                // не остаться результатов, и пользователь увидел бы пустой список.
                this.entries.pagination.page = 1;
                this.scheduleFilterPosts();
            },
            deep: true,
        },
        'entries.pagination': {
            handler() {
                this.scheduleFilterPosts();
            },
            deep: true,
        },
    },
    methods: {
        /**
         * Общая точка входа для обоих наблюдателей: откладывает запрос на 400 мс
         * и отменяет предыдущий отложенный. Заодно склеивает два срабатывания
         * (смена фильтра + сброс страницы) в один запрос.
         */
        scheduleFilterPosts() {
            clearTimeout(this.timerId);
            this.timerId = setTimeout(this.filterPosts, 400);
        },
        filterPosts() {
            // params: this.entries — axios развернёт вложенный объект
            // в filters[title]=…&pagination[page]=2 сам.
            axios
                .get(route('admin.posts.index'), { params: this.entries })
                .then((res) => {
                    // res.data — это { data, links, meta }: строка не изменилась
                    // с 19-го урока, изменилась форма того, что в неё кладётся.
                    this.postsData = res.data;
                })
                .catch((e) => {
                    console.log(e.response?.data);
                });
        },
        // excerpt() и formatDate() — без изменений.
    },
};
</script>
```

И поля фильтра в шаблоне переезжают на новый путь:

```vue
<input v-model="entries.filters.title" type="text" … />
<input v-model="entries.filters.published_at_from" type="date" … />
<input v-model.number="entries.filters.likes_from" type="number" min="0" … />
```

Заодно `per_page` перестаёт быть мёртвым параметром — под него нужен элемент управления. В блок фильтра, четвёртой колонкой:

```vue
<label class="block">
    <span class="mb-1 block text-xs uppercase tracking-wider text-gray-500">
        На странице
    </span>
    <!--
        @change сбрасывает страницу: после «по 50 записей» третьей страницы
        может уже не существовать. Наблюдатель за pagination при этом
        сработает один раз — оба изменения попадут в один debounce.
    -->
    <select
        v-model.number="entries.pagination.per_page"
        class="w-full border border-gray-300 px-3 py-2 text-sm"
        @change="entries.pagination.page = 1"
    >
        <option :value="5">5</option>
        <option :value="10">10</option>
        <option :value="25">25</option>
    </select>
</label>
```

Не забыть поправить сетку: `sm:grid-cols-3` → `sm:grid-cols-4`.

Что здесь изучается:

- **Один объект `entries` — один `params`.** Раньше в `params` уезжал `this.filter`, и добавление `page` означало ручную склейку. Теперь `params: this.entries` покрывает весь контракт: добавили поле в `data()` и правило в реквест — и всё.
- **Как axios сериализует вложенные объекты.** По умолчанию он превращает `{ filters: { title: 'x' } }` в `filters[title]=x` (скобочная нотация), а PHP разбирает такую строку обратно в массив. Ключи со значением `null` axios не отправляет вовсе — поэтому незаполненное поле `likes_from` просто не попадёт в запрос, а пустую строку `title=` доведёт до `null` серверный `ConvertEmptyStringsToNull` (разбиралось в 19-м уроке).
- **`:value="5"`, а не `value="5"`.** Без двоеточия в `<option>` уедет строка `"5"`. Правило `integer` строку пропустит, но `v-model.number` тогда бессмыслен, а сравнение на клиенте начнёт удивлять. Числовые значения задаём биндингом.
- **`postsData` теперь объект, а не массив.** Это по-прежнему копия ссылки на объект пропса, и безопасно это по той же причине, что и в 19-м уроке: мы всегда **заменяем** `postsData` целиком, а не мутируем его.

## 11. Грабли

- **В ответе есть `data`, но нет `meta` и `links`** — остался `->resolve()` в контроллере. Он разворачивает ресурс в голый массив элементов и выбрасывает всё остальное.
- **`postsData.meta is undefined` при первом рендере** — проп `posts` не пришёл (или пришёл массивом), а `default` у пропса задан как `[]`. Заглушка обязана повторять форму настоящего ответа.
- **В таблице пусто, хотя в Network видно 13 постов** — забыт переход `v-for="post in postsData"` → `postsData.data`.
- **«Всего: undefined»** — `postsData.length` у объекта не существует; нужен `postsData.meta.total`.
- **422 при клике по «Previous» или «Next»** — в `page` записан `link.label` (строка `&laquo; Previous`) вместо `link.page`.
- **`Undefined array key "filters"` на первом же заходе** — самая частая грабля этого урока, и лечится она **не** добавлением правила на контейнер: правило `'filters' => ['nullable', 'array']` в паре с вложенными `filters.*` как раз и заставляет `validated()` пропустить блок (п.9). На пустой форме вложенных ключей нет, собирать блок не из чего — нужен `$data['filters'] ?? []` в контроллере или `$request->validated('filters', [])`.
- **Список игнорирует фильтр, хотя в Network видно `filters[title]=…`** — на клиенте блок назван `filter`, а правила и контроллер ждут `filters`. Ошибки не будет: `validated()` не найдёт ключа, `AbstractFilter` не найдёт своих — вернётся неотфильтрованный список. Имена в `entries` обязаны совпадать с правилами буква в букву.
- **Нулевая или отрицательная страница «работает»** — да, так и есть, ошибки не будет (п.3): `paginate()` подменит пустой `$page` резолвером, `Query\Builder::offset()` обрежет смещение до нуля, паджинатор нормализует `current_page` до 1. Именно поэтому `min:1` нужен в правилах: без него сервер молча отдаёт первую страницу вместо 422, и рассинхрон клиента с сервером приходится ловить глазами.
- **`Trying to access array offset on value of type null` в логах** — в `prepareForValidation()` написано `$this->pagination['page'] ?? 1`, а блока `pagination` в запросе нет. Использовать `$this->input('pagination.page', 1)`.
- **Фильтр перестал применяться после рефакторинга** — контроллер всё ещё зовёт `filter($data)` вместо `filter($data['filters'] ?? [])`. Ошибки не будет: `AbstractFilter` не найдёт своих ключей на верхнем уровне и вернёт запрос без условий.
- **Клик по фильтру шлёт два запроса** — наблюдатели зовут `filterPosts()` напрямую, а не общий отложенный `scheduleFilterPosts()`. Видно во вкладке Network: два одинаковых GET подряд.
- **Пустая страница после сужения фильтра** — не сбрасывается `page`. Пагинатор в этом случае честно вернёт `data: []` и `current_page: 3`; ошибки не будет, просто на экране ничего.
- **Записи дублируются между страницами** — из цепочки исчез `latest('id')`. `offset` без `order by` не даёт никаких гарантий.
- **Переключатель мигает или прокручивается вверх** — не наш случай (страница не перезагружается), но если появится: значит вместо axios где-то сработала обычная ссылка `link.url`.

## 12. Что можно сделать лучше

Ниже — не задачи урока, а направления, куда эта реализация растёт.

**Ходить по `link.url` вместо ручной сборки параметров.** Пагинатор уже построил готовые URL для каждой страницы. Если добавить `->withQueryString()`, он допишет в них текущие query-параметры, включая фильтр:

```php
->paginate($perPage, ['*'], 'page', $page)
->withQueryString();
```

Тогда клиенту не нужно знать про `page` вообще:

```js
goToPage(link) {
    if (!link.url || link.active) return;
    axios.get(link.url).then(res => { this.postsData = res.data; });
}
```

Меньше кода, меньше мест, где номер страницы может рассинхронизироваться. Взамен клиент теряет возможность собрать произвольный запрос — но ему это и не нужно.

**Убрать `wantsJson()` и вернуться в Inertia.** Сейчас один экшен обслуживает два формата, а состояние списка живёт только в компоненте: F5, «назад» и отправленная коллеге ссылка фильтр и страницу не сохранят. Штатный инертийный способ решает всё разом:

```js
router.get(route('admin.posts.index'), this.entries, {
    preserveState: true,   // компонент не пересоздаётся, фокус в поле не теряется
    preserveScroll: true,
    replace: true,         // не засоряем историю браузера каждой буквой
    only: ['posts'],       // с сервера приезжает один проп, а не вся страница
});
```

Адрес меняется, `postsData` и ветка `wantsJson()` становятся не нужны — проп `posts` обновляет сервер. Мы делаем через axios сознательно (сначала механика, потом инструмент, который её прячет), но в реальном проекте это первый кандидат на переделку.

**Вынести переключатель в отдельный компонент.** `Pagination.vue`, принимающий `meta` пропсом и отдающий выбранную страницу через `emit`:

```vue
<Pagination :meta="postsData.meta" @change="entries.pagination.page = $event" />
```

Список постов — не последняя таблица в админке: дальше будут категории, теги, пользователи. Компонент окупится на второй же странице, и это ровно тот случай, когда абстракцию заводить уже пора.

**`simplePaginate()`, если общий счётчик не нужен.** Он не делает запрос `count(*)` и отдаёт только «назад/вперёд». На большой таблице подсчёт всех подошедших строк — самая дорогая часть пагинации, особенно с фильтром по количеству лайков, где в `where` стоит коррелированный подзапрос.

**`cursorPaginate()` для больших объёмов.** `offset 100000` заставляет PostgreSQL прочитать и выбросить сто тысяч строк — время растёт линейно с номером страницы. Курсорная пагинация вместо `offset` строит `where id < :last_id`, работает по индексу и не «съезжает», когда во время листания кто-то добавил пост. Цена: только «назад/вперёд», без номеров страниц, и обязательная сортировка по уникальной колонке.

**Ограничить `per_page` списком допустимых значений.** `max:100` защищает от откровенного абсурда, но `Rule::in([5, 10, 25])` честнее описывает контракт: сервер принимает ровно то, что предлагает `<select>`.

**Обрезать `meta`.** В ответе едут `path`, `from`, `to`, `first_page_url` — клиенту они не нужны. Метод `paginationInformation()` в ресурсной коллекции позволяет оставить только `current_page`, `last_page`, `total` и `links`. На учебных объёмах это микрооптимизация, но полезно знать, что форма ответа настраивается.

**Гонка ответов — теперь заметнее.** Проблема из 19-го урока никуда не делась: два запроса в полёте, порядок ответов не гарантирован. Раньше это грозило устаревшим списком, теперь — ещё и рассинхроном между `entries.pagination.page` и `postsData.meta.current_page`, то есть подсвеченная кнопка перестанет соответствовать содержимому таблицы. Лечится счётчиком запросов или `AbortController`.

**Индикатор загрузки.** Между кликом по номеру страницы и обновлением таблицы проходит 400 мс debounce плюс время запроса. Для набора текста задержка оправданна, для клика по кнопке — раздражает. Разумный компромисс: разные задержки для разных источников (`scheduleFilterPosts(400)` для фильтра, `scheduleFilterPosts(0)` для пагинации) плюс флаг `loading`, снимаемый в `.finally()`.

**Подсвечивать активную страницу по серверу, а не по клиенту.** Сейчас активность приходит в `link.active` из ответа — это правильно и уже так работает. Соблазн завести собственное сравнение `link.page === entries.pagination.page` стоит гасить: клиентское состояние опережает серверное, и на медленной сети кнопка подсветится раньше, чем приедут данные.
