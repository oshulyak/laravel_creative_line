# Lesson 29 - Очереди, задачи и расписание

Цель урока: письмо автору комментария перестаёт задерживать ответ. Пользователь нажимает «Отправить», комментарий появляется мгновенно, а письмо уходит отдельным фоновым процессом. Урок начинается с проблемы, которую мы специально оставили в 28-м: запрос ждёт SMTP-сервер.

По пути разбираются: **очередь** — из чего она состоит и что происходит в момент `dispatch()`; таблица `jobs` по колонкам; **воркер** и разница `queue:work` / `queue:listen`; `failed_jobs`, попытки и таймауты; именованные очереди; **пачки и цепочки** (`Bus::batch()`, `Bus::chain()`); приём «одна строка — одна задача»; **расписание** в `routes/console.php` и чем оно принципиально отличается от очереди; **cron** — одна строка в системе на весь проект; **Supervisor** — почему без него воркер на проде не живёт; и напоследок — каст `published_at` у `Post`.

Отправная точка — состояние после 28-го урока.

Главная мысль урока, ради которой всё остальное: **Laravel ничего не выполняет в фоне сам**. Ни одна задача из очереди и ни одна строка расписания не запустится, пока рядом не работает отдельный процесс, который их разбирает. Половина недоразумений с очередями — от ожидания, что «оно как-то само».

# Часть I. Очередь: работа, которую делают не в запросе

## 2. Проблема

Откройте пост и оставьте комментарий. Между нажатием кнопки и появлением комментария — заметная пауза, секунда-две. Комментарий при этом пишет «2 секунды назад», и он не врёт: запись в базе появилась сразу, а ответ до браузера всё это время не доходил.

Что происходило в паузе, видно по коду `CommentController::store()`:

```php
$comment = $post->comments()->create($request->validated());   // быстро, миллисекунды

Mail::to($post->author->user)->send(new StoreCommentMail(...)); // ← вот здесь пауза

return response()->json(...);                                   // сюда дошли только теперь
```

`send()` открывает TCP-соединение с `connect.smtp.bz`, авторизуется, передаёт письмо и ждёт подтверждения. Это **обращение к стороннему сервису**, и суть проблемы не в почте: то же самое будет с платёжным шлюзом, генерацией PDF, выгрузкой в Excel, запросом к чужому API. Чужой сервер отвечает, когда ему удобно.

Вторая форма той же проблемы — долгая работа внутри самого приложения. Экспорт постов в Excel: пользователь жмёт кнопку и сидит с занятым окном, пока приложение собирает десятки тысяч строк. Уйти со страницы нельзя, обновить нельзя, а если моргнёт свет — начинать заново.

Теперь важное различие, которое и подсказывает решение. У запроса «добавить комментарий» есть:

- **основной сценарий** — комментарий должен появиться. Пользователь ради этого пришёл;
- **сопутствующий** — автора неплохо бы уведомить. Он прочитает письмо через десять минут, через час или вообще на следующей неделе.

Сейчас сопутствующий сценарий держит основной в заложниках. Решение — разорвать эту связь: ответ отдать сразу, а письмо поручить кому-то другому. Этот «кто-то другой» и есть очередь.

## 3. Из чего состоит очередь

Участников три, и путать их не стоит — почти все вопросы по теме сводятся к тому, что человек держит в голове двух вместо трёх.

**1. Диспетчер.** Работает внутри запроса. Строка `SendCommentMailJob::dispatch($post, $comment)` берёт объект задачи, сериализует его и **записывает** — одной вставкой в базу. Управление возвращается немедленно.

**2. Хранилище задач.** Куда именно записывает — решает `QUEUE_CONNECTION` в `.env`:

| Значение | Куда кладёт |
| --- | --- |
| `database` | таблица `jobs` — наш вариант |
| `redis` | список в Redis; быстрее, типичный выбор для нагруженного прода |
| `sqs`, `beanstalkd` | внешние очереди |
| `sync` | **никуда**: выполняет задачу немедленно, прямо в запросе |
| `null` | выбрасывает задачу |

`sync` — это «очередь-обманка», и она пригодится дальше в тестах.

**3. Воркер.** Отдельный долгоживущий процесс, запускаемый командой `php artisan queue:work`. В цикле: спроси хранилище, есть ли работа → возьми задачу → пометь занятой → выполни `handle()` → удали.

Как это выглядит во времени:

```
Браузер ──POST /posts/5/comments──▶ Laravel (запрос)
                                      │
                                      ├─ INSERT в comments
                                      ├─ dispatch() → INSERT в jobs   ← миллисекунды
                                      │
   Браузер ◀─────── 201 Created ──────┘   запрос закончился


   ( параллельно, в другом процессе, живущем своей жизнью )

   php artisan queue:work  ──▶ SELECT из jobs: «есть работа?»
                           ──▶ UPDATE reserved_at: «беру, не трогать»
                           ──▶ handle() → SMTP (две секунды — и пусть)
                           ──▶ DELETE: строка исчезла
```

Отсюда главный вывод: **`dispatch()` — это не «запустить в фоне», а «записать в список дел»**. Выполнится задача или нет, зависит только от того, работает ли воркер. Если воркера нет, строки в `jobs` копятся молча и бесконечно — ни ошибки, ни предупреждения.

Локально воркер уже поднимается за вас: в `composer.json` в скрипте `dev` рядом с Vite стоит `php artisan queue:listen`. Поэтому в `composer run dev` всё заработает само, и об этом легко забыть — а потом полдня искать, почему на чистом `php artisan serve` письма не уходят.

## 4. Таблица `jobs` по колонкам

Посмотрите её после первого же комментария — механика перестаёт быть магией:

| Колонка | Что значит |
| --- | --- |
| `id` | порядковый номер. Он же определяет порядок разбора: первым пришёл — первым ушёл, отсюда и слово «очередь» |
| `queue` | имя очереди. Строка. Если не указали — Laravel пишет `default` |
| `payload` | JSON: полное имя класса задачи и её сериализованное состояние |
| `attempts` | сколько раз воркер уже брал эту задачу в работу. Пока не брал — `0` |
| `reserved_at` | момент, когда задачу взяли в работу. `NULL` — свободна |
| `available_at` | с какого момента задачу можно брать. Обычно равен `created_at`; отличается, если задачу отложили |
| `created_at` | когда положили в очередь |

Две колонки стоит понять отдельно.

**`reserved_at` — защита от дублей.** Воркеров можно запустить несколько параллельно, и без пометки «занято» двое могли бы взять одну задачу и отправить два письма. Воркер, забирая задачу, ставит `reserved_at`; остальные её больше не видят.

**`available_at` — отложенный запуск.** `dispatch(...)->delay(now()->addMinutes(10))` кладёт задачу сразу, но с `available_at` на десять минут вперёд. До этого момента воркер её игнорирует. Полезно для «письма-напоминания через сутки».

## 5. `SendCommentMailJob`: сама задача

```
php artisan make:job SendCommentMailJob --no-interaction
```

Класс попадает в `app/Jobs/`. Папка и неймспейс `App\Jobs` зарезервированы Laravel — регистрировать задачу нигде не нужно, она находится по имени класса.

О названии. В проекте у нас принято раскладывать классы по подпапкам (`App\Mail\Comment\StoreCommentMail`, `App\Http\Requests\Client\Comment\StoreRequest`), но для задач я оставляю плоскую структуру и **длинное имя**. Причина в том, как задача выглядит в месте вызова:

```php
SendMailJob::dispatch($post, $comment);        // какое письмо? кому? откуда?
SendCommentMailJob::dispatch($post, $comment); // видно, не открывая файл
```

Имя задачи читают в контроллере, а подпапку там не видно. Когда задач по комментариям станет несколько, появится и папка `app/Jobs/Comment/` — но имена всё равно останутся самодостаточными.

`app/Jobs/SendCommentMailJob.php`:

```php
<?php

namespace App\Jobs;

use App\Mail\Comment\StoreCommentMail;
use App\Models\Comment;
use App\Models\Post;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Mail;

/**
 * Отправляет автору публикации письмо о новом комментарии.
 *
 * implements ShouldQueue — то самое, что отличает задачу в очереди от обычного
 * класса. Без этого интерфейса dispatch() выполнил бы handle() прямо здесь
 * и сейчас, и мы бы ничего не выиграли. Заготовка make:job ставит его сама:
 * с 11-й версии Laravel считает очередь поведением по умолчанию (обычный,
 * неочередной класс даёт флаг --sync).
 */
class SendCommentMailJob implements ShouldQueue {
    /**
     * Queueable — набор из четырёх трейтов сразу:
     *   Dispatchable       — статический dispatch() и его варианты;
     *   InteractsWithQueue — доступ к самой задаче изнутри handle(): attempts(), release(), fail();
     *   Queueable          — onQueue(), delay(), onConnection();
     *   SerializesModels   — правила сериализации моделей, о них п. 7.
     */
    use Queueable;

    /**
     * Конструктор — единственное место, где задача получает данные. Всё, что
     * здесь окажется, уедет в payload и вернётся к воркеру.
     *
     * Свойства можно объявлять private: в отличие от Mailable, у задачи нет
     * Blade-шаблона, которому нужны публичные свойства. Но в тестах удобнее
     * public — проверка «задача поставлена именно для этого поста» пишется
     * тогда в одну строку. Оставляю public осознанно, ради теста из п. 20.
     */
    public function __construct(
        public Post $post,
        public Comment $comment,
    ) {}

    /**
     * Тело задачи. Внутри — ровно тот код, который раньше стоял в контроллере.
     *
     * Ничего «особенного для фона» здесь нет: Laravel выполнит этот метод
     * сверху вниз точно так же, как выполнил бы его в экшене. Разница только
     * в том, КОГДА и В КАКОМ процессе это произойдёт.
     *
     * send(), а не queue(): мы уже внутри очереди, торопиться больше некуда
     * и ждать SMTP-сервер здесь совершенно нормально.
     */
    public function handle(): void {
        Mail::to($this->post->author->user)
            ->send(new StoreCommentMail($this->post, $this->comment));
    }
}
```

## 6. Контроллер: одна строка вместо отправки

В `app/Http/Controllers/Client/CommentController.php` метод `store()`:

```php
        // Было: Mail::to($post->author->user)->send(new StoreCommentMail($post, $comment));
        //
        // dispatch() кладёт задачу в jobs и сразу возвращает управление. Условие
        // «не пишем автору о его же комментарии» остаётся здесь, а не переезжает
        // внутрь задачи: это правило про то, НУЖНО ЛИ уведомление, и решать его
        // дешевле до записи в очередь, чем создавать задачу ради ничего.
        if ($post->author_id !== $comment->author_id) {
            SendCommentMailJob::dispatch($post, $comment);
        }
```

Импорты: `use App\Jobs\SendCommentMailJob;` появляется, `use App\Mail\Comment\StoreCommentMail;` и `use Illuminate\Support\Facades\Mail;` — уходят: обоими теперь пользуется задача.

Больше в контроллере не меняется ничего. Это и есть весь «переезд в фон»: строку вырезали из экшена и вставили в `handle()`.

Варианты вызова, которые пригодятся дальше:

```php
SendCommentMailJob::dispatch($post, $comment);                          // обычный
SendCommentMailJob::dispatch($post, $comment)->onQueue('mail');         // в именованную очередь
SendCommentMailJob::dispatch($post, $comment)->delay(now()->addHour()); // не раньше чем через час
SendCommentMailJob::dispatchSync($post, $comment);                      // немедленно, мимо очереди
SendCommentMailJob::dispatchAfterResponse($post, $comment);             // после ответа, но в том же процессе
```

`dispatchAfterResponse()` — промежуточный вариант без воркера: PHP отдаёт ответ браузеру и доделывает работу «на выдохе». Годится для мелочи вроде одного письма и не годится для чего-то тяжёлого: процесс всё ещё занят, и падение никуда не записывается.

## 7. Что именно уезжает в очередь

`SerializesModels` внутри `Queueable` — не формальность, а деталь, которая определяет поведение.

Когда задача сериализуется, Eloquent-модели **не** попадают в `payload` целиком. Уезжает только имя класса и идентификатор; воркер в момент выполнения достаёт запись из базы заново.

Плюс: письмо уйдёт с актуальными данными, а не с теми, что лежали в памяти минуту назад.

Минус: если пост или комментарий успели удалить, воркер не найдёт модель, и задача упадёт с `ModelNotFoundException`. Для уведомления это правильное поведение — письма про удалённый комментарий быть не должно.

Правило отсюда простое: **в конструктор задачи кладут модели и скаляры, а не то, что не переживёт сериализацию** — открытые файлы, замыкания, объекты запроса. И не кладут ничего большого: `payload` — это строка в базе, а не место для мегабайтного массива.

## 8. Запуск воркера: `queue:work` и `queue:listen`

```
php artisan queue:work
```

Процесс занимает окно терминала и висит. При появлении задачи печатает строку с классом и результатом (`DONE` / `FAIL`).

Вторая команда делает то же самое, но иначе устроена:

```
php artisan queue:listen
```

| | `queue:work` | `queue:listen` |
| --- | --- | --- |
| Приложение | поднимает один раз и держит в памяти | поднимает заново под каждую задачу |
| Скорость | быстрее | медленнее |
| Видит ли изменения кода | **нет**, до перезапуска | да, всегда свежий код |
| Падение внутри задачи | может уронить процесс | убивает только дочерний процесс |
| Где применять | прод, под присмотром Supervisor | разработка |

**Ловушка, которую надо пройти один раз.** Работает `queue:work`. Вы правите `handle()` — добавляете свойство, меняете логику. Задача падает с чем-то в духе `Typed property App\Jobs\SendCommentMailJob::$post must not be accessed before initialization`. Кода такого уже нет, а ошибка есть. Причина: воркер держит в памяти **старую** версию класса и знать не знает о ваших правках. Лечится только перезапуском:

```
php artisan queue:restart
```

`queue:restart` не убивает процесс грубо — он просит воркеров мягко завершиться после текущей задачи. Поднимет их обратно уже Supervisor (п. 19). Именно из-за этой ловушки в разработке используют `listen`: он поднимает приложение заново под каждую задачу и всегда видит актуальный код. В `composer.json` проекта стоит именно `queue:listen`.

Опции воркера (`php artisan queue:work --help`) — их стоит прочитать глазами хотя бы раз:

| Опция | По умолчанию | Что делает |
| --- | --- | --- |
| `--queue=` | `default` | какие очереди разбирать; через запятую — по приоритету |
| `--tries=` | `1` | сколько раз пробовать задачу до `failed_jobs` |
| `--timeout=` | `60` | сколько секунд отводится **одной** задаче |
| `--memory=` | `128` | предел памяти на воркер, МБ |
| `--sleep=` | `3` | сколько спать, когда задач нет |
| `--backoff=` | `0` | пауза перед повторной попыткой упавшей задачи |
| `--max-jobs=` | `0` (без предела) | сколько задач сделать и выйти |
| `--max-time=` | `0` (без предела) | сколько секунд прожить и выйти |
| `--stop-when-empty` | — | выйти, когда очередь опустела |
| `--once` | — | сделать одну задачу и выйти |

Два наблюдения, которые экономят время.

**Воркер — процесс конечный, и это норма.** Он завершается по `--max-time`, по `--max-jobs`, по превышению памяти, после `queue:restart`, при обрыве соединения с базой, при фатальной ошибке. Планировать нужно не «чтобы не падал», а «чтобы поднимался обратно» — этим занимается Supervisor.

**`--timeout=60` — про одну задачу, а не про воркера.** Задача, которая работает дольше минуты, будет прервана. Для тяжёлых выгрузок таймаут поднимают: флагом воркера или свойством на классе задачи (`public $timeout = 300;`).

## 9. Когда задача падает: `failed_jobs`

Задача бросила исключение. Воркер смотрит на число попыток: если они исчерпаны — строка переезжает из `jobs` в `failed_jobs`. По умолчанию попытка ровно одна, то есть первое же исключение отправляет задачу в брак.

Колонки `failed_jobs`: `uuid`, `connection`, `queue`, `payload`, **`exception`**, `failed_at`. `exception` — первое место, куда идти: там лежит полный стек-трейс, в том же виде, в каком Laravel показывает ошибки в браузере.

Команды для работы с браком:

```
php artisan queue:failed              # список
php artisan queue:retry <uuid>        # вернуть одну задачу в очередь
php artisan queue:retry all           # вернуть все
php artisan queue:forget <uuid>       # удалить одну
php artisan queue:flush               # очистить таблицу целиком
```

Настройки попыток — на классе задачи, они важнее флагов воркера:

```php
class SendCommentMailJob implements ShouldQueue {
    use Queueable;

    /** Сколько раз пробовать. */
    public int $tries = 3;

    /** Пауза перед повторами: 10 секунд, потом 30, потом 60. */
    public array $backoff = [10, 30, 60];

    /** Сколько секунд отводится одной попытке. */
    public int $timeout = 120;
}
```

Для письма три попытки осмысленны: почтовый сервер мог быть недоступен минуту. Для задачи, которая списывает деньги, — нет: повтор означает второе списание. Это решение по существу, а не по умолчанию.

Отдельная ошибка, которую стоит узнавать в лицо: **`MaxAttemptsExceededException`** («слишком много попыток»). Часто она появляется не потому, что задача много раз падала, а потому, что воркер умер, **уже зарезервировав** задачу. Строка осталась с `reserved_at` и увеличенным `attempts`; следующий воркер видит, что лимит исчерпан, и отправляет её в брак. Ровно это происходит, когда правишь код при живом `queue:work`.

## 10. Именованные очереди

Очередь — это просто строка в колонке `queue`. Не указали — Laravel пишет `default`.

```php
SendCommentMailJob::dispatch($post, $comment)->onQueue('mail');
```

или свойством на классе:

```php
public string $queue = 'mail';
```

И вот грабли, на которые наступают все:

```
php artisan queue:work                  # разбирает ТОЛЬКО очередь default
php artisan queue:work --queue=mail     # разбирает mail
php artisan queue:work --queue=mail,default   # сначала mail, потом default
```

Команда без `--queue` не означает «разбирай всё». Она означает «разбирай `default`». Задача уехала в `mail`, воркер смотрит в `default`, в терминале тишина, в таблице растёт список — и непонятно, что сломалось. Не сломалось ничего: они просто смотрят в разные места.

Зачем вообще имена: чтобы разделить важное и долгое. Письма и уведомления — в быструю очередь с несколькими воркерами; ночные выгрузки — в отдельную, где одна задача может работать полчаса и никого не задерживать. Соглашений об именах нет, пишите строчными буквами и по смыслу: `mail`, `imports`, `reports`.

## 11. Пачки и цепочки

Два способа запускать несколько задач вместе. Оба — про форму обработки, механика под ними та же.

**Пачка (batch)** — задачи выполняются вперемешку, порядок не гарантирован, зато у всей группы есть общий результат:

```php
use Illuminate\Support\Facades\Bus;

Bus::batch([
    new ImportRowJob($row1),
    new ImportRowJob($row2),
    new ImportRowJob($row3),
])->then(function ($batch) {
    // все задачи выполнены успешно
})->catch(function ($batch, $e) {
    // первая упавшая задача
})->finally(function ($batch) {
    // пачка завершена — неважно, чем
})->dispatch();
```

Главное условие: **задачи внутри пачки не должны зависеть друг от друга**. Порядок произвольный, параллельность — тоже. Состояние пачки хранится в таблице `job_batches` (она уже есть в проекте), заготовку такой задачи даёт `make:job --batched`.

**Цепочка (chain)** — строго по очереди, следующая начинается только после успеха предыдущей:

```php
Bus::chain([
    new PrepareReportJob($profile),
    new RenderReportJob($profile),
    new SendReportJob($profile),
])->dispatch();
```

Упало звено — цепочка останавливается, оставшиеся задачи не выполняются. Это ровно то, что нужно, когда третий шаг бессмыслен без второго.

Выбор между ними: **пачка — когда важен общий итог, цепочка — когда важен порядок**. В нашем проекте пока не нужно ни то, ни другое; знать про них стоит, чтобы не изобретать их вручную через флаги в базе.

## 12. Приём «одна строка — одна задача»

Второе применение очередей, уже не про интерфейс, а про надёжность. Оно менее очевидно и на практике выручает чаще.

Задача: забрать у внешнего сервиса 100 000 объектов, каждый обработать и положить в базу.

Наивный вариант — один длинный процесс. Что с ним не так: на 999-м объекте приходит запись, где число внезапно оказалось строкой, а нужный ключ пропал. Процесс падает. Обработано девятьсот с чем-то, в каком состоянии база — надо разбираться. Чините, запускаете заново — падает на 1400-м по новой причине. И так по кругу.

Вариант с очередью: пробегаете по данным и на **каждый объект** создаёте задачу.

```php
foreach ($rows as $row) {
    ImportRowJob::dispatch($row);
}
```

Что меняется:

- падение одной задачи не трогает остальные 99 999;
- все упавшие лежат в `failed_jobs` с текстом исключения — видно, что именно пришло не так;
- починили причину — `queue:retry all`, и они доедут;
- в любой момент понятно, сколько прошло и сколько нет.

Создавать десятки тысяч задач не страшно и не расточительно — механизм для этого и сделан. Формулировка результата, которую обычно ждёт заказчик, звучит как «загрузили 98%, остальные 2% не прошли по таким-то причинам», и она гораздо лучше, чем «процесс упал посередине».

## 13. Очередь для слушателей и обсерверов

`dispatch()` — не единственный способ отправить работу в фон. Тот же `ShouldQueue` работает на слушателях событий:

```php
class SendCommentNotification implements ShouldQueue {
    public function handle(CommentCreated $event): void { /* ... */ }
}
```

Событие сработает синхронно, а слушатель с `ShouldQueue` не выполнится сразу — он уедет в очередь и выполнится воркером. Так же можно пометить и обсервер модели: тогда реакция на `created`/`updated` перестанет задерживать запрос.

Почему в нашем проекте отправка стоит прямо в контроллере, а не в слушателе: событий на «создан комментарий» пока одно-единственное следствие. Связка событие + слушатель окупается со второго следствия, и тогда `ShouldQueue` на слушателе — самый дешёвый способ сделать всю ветку фоновой.

# Часть II. Расписание: работа, которую делают по времени

## 14. Где живёт расписание

Вторая половина урока — про консольные команды. Мы их уже писали (`app/Console/Commands/MyTest.php`), но использовали для экспериментов. Настоящее их назначение — **работа по расписанию**: раз в сутки посчитать статистику, раз в час выгрузить отчёт, раз в неделю почистить старые записи.

В Laravel 10 и раньше расписание описывали в `app/Console/Kernel.php` (тот самый «кернел», которых было два — консольный и HTTP). В Laravel 11+ консольного кернела нет, расписание живёт в `routes/console.php`:

```php
<?php

use Illuminate\Support\Facades\Schedule;

Schedule::command('my:test')->everyMinute();
```

Это временная запись — поэкспериментировать и убрать. Читается она буквально: «команду `my:test` запускать каждую минуту». Первым аргументом идёт **сигнатура команды** — ровно то, что вы пишете после `php artisan`.

Интервалов Laravel заготовил на все случаи: `everySecond()`, `everyTenSeconds()`, `everyMinute()`, `everyFifteenMinutes()`, `hourly()`, `daily()`, `dailyAt('03:00')`, `weeklyOn(1, '8:00')`, `monthly()`, `yearly()`. Плюс модификаторы: `->weekdays()`, `->between('8:00', '17:00')`, `->timezone('Europe/Moscow')`.

Если нужного интервала не нашлось, есть аварийный выход — синтаксис cron напрямую:

```php
Schedule::command('my:test')->cron('0 3 * * *');   // каждый день в 3:00
```

Пять полей: минута, час, день месяца, месяц, день недели. `* * * * *` — каждую минуту. Язык лаконичный и нечитаемый; методы Laravel существуют именно затем, чтобы его не писать.

Проверить, что Laravel вашу запись увидел:

```
php artisan schedule:list
```

Команда покажет таблицу: выражение cron, команда, время следующего запуска. Это первое, что нужно делать после правки `routes/console.php` — опечатка в имени команды видна сразу.

## 15. Что запускает расписание

И вот ключевой момент, из-за которого расписание чаще всего «не работает».

`routes/console.php` — это **декларация**. Она описывает, что и когда должно запускаться, и ничего не запускает. Нужен процесс, который будет её читать и сверять со временем.

Такой процесс — команда:

```
php artisan schedule:run
```

Она делает ровно одно: смотрит на текущее время, проходит по всем записям расписания, выбирает те, которым пора, запускает их и **завершается**. Это короткий процесс на один такт, не демон.

Дальше вопрос: кто зовёт `schedule:run`? Каждую минуту его должен звать кто-то извне — на проде это cron (п. 17). Локально cron'а под рукой нет (а на Windows его нет вовсе), поэтому есть эмулятор:

```
php artisan schedule:work
```

`schedule:work` — простой цикл: он сам вызывает `schedule:run` раз в минуту, пока вы его не остановите. Это «карманный cron» для разработки, и **на проде его не используют**.

Заметная деталь: `schedule:work` запускается в любую секунду, но первая задача выполнится не сразу, а с началом новой минуты. Cron мыслит минутами, и Laravel это повторяет.

Про интервалы меньше минуты (`everySecond()`, `everyTenSeconds()`): их придумали позже, и работают они хитро — `schedule:run`, обнаружив такие записи, не завершается сразу, а доживает текущую минуту, запуская их внутри неё. Снаружи всё равно одна минута — один вызов.

Полезные соседи:

```
php artisan schedule:list         # что зарегистрировано и когда запустится
php artisan schedule:run          # один такт вручную — удобно для отладки
php artisan schedule:work         # цикл раз в минуту (локальная замена cron)
php artisan schedule:test         # выполнить выбранную задачу прямо сейчас
php artisan schedule:interrupt    # прервать текущее выполнение
```

## 16. Чем расписание отличается от очереди

Две темы урока похожи внешне — обе «что-то происходит не в запросе» — и разные по сути. Различие проще всего держать в голове через вопрос **«что служит поводом?»**

| | **Очередь** (queue) | **Расписание** (schedule) |
| --- | --- | --- |
| Повод | событие: кто-то что-то сделал | время: наступил момент |
| Кто инициирует | код приложения, `dispatch()` | часы |
| Сколько раз выполнится | ровно столько, сколько раз позвали | по календарю, бесконечно |
| Что выполняется | класс-задача из `app/Jobs` | консольная команда (или замыкание) |
| Где хранится «что делать» | строка в таблице `jobs` | код в `routes/console.php` |
| Есть ли очередь как список | да, это её суть | нет, ничего не копится |
| Кто выполняет | воркер `queue:work` — долгоживущий процесс | `schedule:run` — короткий процесс на один такт |
| Кто запускает исполнителя на проде | **Supervisor** (держит процесс живым) | **cron** (зовёт раз в минуту) |
| Что с ошибками | попытки, потом `failed_jobs` | ничего: упало и упало, смотрите логи |

Формулировка на память: **очередь отвечает на вопрос «не сейчас», расписание — на вопрос «регулярно»**.

Примеры из нашего проекта:

- «отправить письмо о комментарии» — повод событийный (появился комментарий). Очередь.
- «раз в сутки посчитать статистику по постам» — повода нет, есть календарь. Расписание.

Ничто не мешает их сочетать, и в реальных проектах так и делают: команда по расписанию просыпается раз в сутки, быстро создаёт пачку задач и завершается, а воркеры разбирают их столько, сколько нужно. Расписание — будильник, очередь — исполнители.

Симметрия по запуску на проде получается такая:

```
РАСПИСАНИЕ                              ОЧЕРЕДЬ
cron ──каждую минуту──▶ schedule:run    supervisor ──держит живым──▶ queue:work
     короткий процесс, завершается            долгий процесс, не завершается
```

Инструменты разные ровно потому, что разные по природе процессы: одному нужно, чтобы его регулярно **звали**, другому — чтобы его **не давали умереть**.

## 17. Cron: одна строка на весь проект

Самый частый вопрос по теме: нужно ли прописывать каждую задачу расписания в cron отдельно?

**Нет.** В cron прописывается **одна-единственная строка на проект**, и она никогда не меняется. Всё остальное живёт в `routes/console.php`, и добавление новых задач туда никакой настройки системы не требует.

Cron — это служба Linux, которая умеет запускать команды по времени. Она есть в любом дистрибутиве. Список её заданий называется crontab и открывается так:

```
crontab -e
```

Строка, которую туда добавляют:

```
* * * * * cd /var/www/line && php artisan schedule:run >> /dev/null 2>&1
```

По частям:

- `* * * * *` — каждую минуту. Минимальный шаг cron — минута, меньше он не умеет;
- `cd /var/www/line` — **абсолютный** путь к проекту. `php artisan` работает только внутри проекта: вне его слово `artisan` системе ничего не говорит;
- `php artisan schedule:run` — тот самый один такт. `php` берётся глобально, из системы;
- `>> /dev/null 2>&1` — выбросить вывод. Иначе cron будет слать письмо после каждого запуска, то есть 1440 писем в сутки. Вместо `/dev/null` можно указать файл лога.

Дальше всё работает так: раз в минуту cron заходит в проект и спрашивает у Laravel «есть что-нибудь на сейчас?». Laravel сверяет время с записями в `routes/console.php` и запускает то, чему пора. Добавили в `routes/console.php` новую задачу — она подхватится **автоматически**, со следующей минуты, без правки crontab и без перезапуска чего-либо.

Отсюда прямой ответ на вопрос урока: **расписание из `console.php` применяется само; руками в cron прописывается только вызов `schedule:run`**.

Что важно помнить:

- **Локально (Laragon, Windows) cron'а нет.** Его заменяет `php artisan schedule:work`. Ровно поэтому урок и показывает две разные команды.
- Cron запускает `schedule:run` **всегда**, каждую минуту, даже когда делать нечего. Это дёшево: Laravel поднимается, видит пустой список и выходит.
- Команда выполняется от имени того пользователя, чей crontab вы правите. Если проект пишет файлы, права должны совпадать с правами веб-сервера.
- Если задача может не уложиться в свой интервал (например, ежеминутная выгрузка иногда идёт три минуты), добавьте `->withoutOverlapping()` — иначе запуски наложатся друг на друга.

## 18. Supervisor: кто следит за воркером

Вторая половина вопроса «а как на проде». С расписанием разобрались — там cron. С очередью так не получится, и вот почему.

Воркер (`queue:work`) — процесс **долгоживущий**. Он должен работать всегда: задача может прийти в любую секунду. Но он обязательно когда-нибудь завершится:

- дошёл до предела памяти (`--memory=128`) или времени (`--max-time`);
- получил `queue:restart` после деплоя;
- задача уронила процесс фатальной ошибкой;
- оборвалось соединение с базой;
- сервер перезагрузили.

Запустить его в терминале по SSH нельзя: закроете сессию — процесс умрёт вместе с ней. Cron тоже не подходит — он умеет **запускать** команды, но не умеет следить, жив ли запущенный процесс, и поднимать его обратно.

Нужен менеджер процессов. В мире Linux это **Supervisor**.

Важно понимать: Supervisor к Laravel не имеет никакого отношения. Это обычная линуксовая программа, которая умеет одно — держать заданные процессы живыми. Ей всё равно, что запускать.

Установка:

```
sudo apt-get install supervisor
```

Конфиги лежат в `/etc/supervisor/conf.d/` — путь стандартный для всех дистрибутивов. Создаём там `laravel-worker.conf`:

```ini
[program:laravel-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/line/artisan queue:work --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=4
redirect_stderr=true
stdout_logfile=/var/www/line/storage/logs/worker.log
stopwaitsecs=3600
```

По строкам:

| Строка | Что значит |
| --- | --- |
| `[program:laravel-worker]` | имя, под которым процесс известен Supervisor. Оно же понадобится в `supervisorctl` |
| `process_name` | шаблон имени для каждой копии: `laravel-worker_00`, `_01`, … |
| `command` | **главная строка**: что запускать. `php` — глобальный, дальше абсолютный путь к `artisan` вашего проекта и обычная artisan-команда с флагами |
| `autostart=true` | поднять при старте системы: сервер перезагрузился — воркеры сами вернулись |
| `autorestart=true` | **ради чего всё затевалось**: процесс завершился — поднять заново |
| `user=www-data` | от чьего имени запускать. В Linux у каждого процесса есть владелец; здесь должен стоять тот же пользователь, под которым живёт приложение (в Docker обычно `root`) |
| `numprocs=4` | сколько воркеров поднять параллельно |
| `stdout_logfile` | куда писать вывод. Первое место, куда смотреть, если воркеры «не работают» |
| `stopwaitsecs=3600` | сколько ждать, пока процесс завершится сам, прежде чем убить. Должно быть больше самой долгой задачи, иначе её оборвут на середине |

Про `numprocs` — предупреждение из практики. Каждый воркер держит в памяти полное приложение Laravel и ест ресурсы всерьёз. Восемь воркеров из документации — это про сервер, которому есть чем их кормить. Разумный старт — **два-четыре**, дальше по нагрузке.

Применяем конфиг:

```
sudo supervisorctl reread        # перечитать файлы конфигов
sudo supervisorctl update        # применить изменения
sudo supervisorctl start laravel-worker:*   # запустить все копии
```

`laravel-worker` в последней команде — это имя из `[program:...]`. Полезные соседи: `supervisorctl status`, `supervisorctl stop laravel-worker:*`, `supervisorctl restart laravel-worker:*`.

Если очередей несколько, файлов конфигурации делают несколько — по одному на очередь, с разными `--queue=` и своим `numprocs`. Письма и тяжёлые выгрузки не должны конкурировать за одних и тех же воркеров.

В Docker всё то же самое: Supervisor ставят внутрь контейнера приложения, конфиг кладут туда же, `user=root` (внутри контейнера разделение прав обычно не нужно), логи — по пути внутри контейнера.

Короткий ответ на вопрос «зачем Supervisor»: **потому что воркер обязан жить всегда, а PHP-процессы смертны, и никто, кроме менеджера процессов, не поднимет его обратно**.

## 19. Итоговая картина запуска

Четыре процесса, которые полезно держать в голове целиком.

**Локально (`composer run dev`):**

```
Laragon (или composer run dev:serve) — отвечает на запросы
npm run dev                          — Vite, сборка фронтенда
php artisan queue:listen             — разбирает очередь (уже в скрипте dev)
php artisan schedule:work            — расписание; запускается отдельно, когда нужно
```

Скрипт `dev` поднимает две последние строки — `queue:listen` и Vite; HTTP отдаёт Laragon. Расписания в скрипте нет: оно нужно не каждый день, и запускать его стоит осознанно.

**На проде:**

```
php-fpm / nginx                              — отвечает на запросы
supervisor → php artisan queue:work × N      — разбирает очередь, всегда живой
cron       → php artisan schedule:run        — раз в минуту, короткий такт
```

Две команды — `queue:work` и `schedule:run` — и два принципиально разных способа их запускать: одну держат живой, вторую регулярно зовут.

## 20. Тесты: задача и письмо — разные вопросы

Тесты из 28-го урока проверяли одно: «после запроса ушло письмо». Теперь запрос письма не отправляет — он ставит задачу. Проверять нужно две вещи по отдельности:

1. контроллер **поставил задачу** (и не поставил там, где не надо);
2. задача **отправляет письмо**.

Сначала неприятная тонкость. В `phpunit.xml` стоит `QUEUE_CONNECTION=sync` — в тестах очередь «обманка», задача выполняется немедленно. Это значит, что старый тест с `Mail::fake()` и `assertSent()` **останется зелёным** и после переезда в очередь: письмо действительно отправится, прямо внутри запроса. Тест не сломается — и именно поэтому его нужно переписать осознанно: сейчас он ничего не знает про задачу и не заметит, если `dispatch()` из контроллера пропадёт.

`tests/Feature/ClientCommentMailTest.php` — первые два теста меняются:

```php
use App\Jobs\SendCommentMailJob;
use Illuminate\Support\Facades\Queue;

    public function test_post_author_is_notified_about_new_comment(): void {
        // Queue::fake() подменяет очередь заглушкой: задачи никуда не уезжают
        // и НЕ выполняются, но фасад запоминает всё, что в него положили.
        // Без него сработал бы драйвер sync, задача выполнилась бы тут же,
        // и мы проверяли бы уже не постановку в очередь, а отправку письма.
        Queue::fake();

        $post = Post::factory()->create(['status' => Post::STATUS_PUBLISHED]);
        $profile = Profile::factory()->create();

            ->postJson(route('client.posts.comments.store', $post), [

        // и именно с этим комментарием. $job->post доступен потому, что
        // свойства конструктора объявлены public.
        Queue::assertPushed(SendCommentMailJob::class, function (SendCommentMailJob $job) use ($post) {
            return $job->post->is($post)
                && $job->comment->content === 'Отличная статья';
        });
    }

    public function test_author_is_not_notified_about_own_comment(): void {
        Queue::fake();

        $post = Post::factory()->create(['status' => Post::STATUS_PUBLISHED]);

        $this->actingAs($post->author->user)
            ->postJson(route('client.posts.comments.store', $post), [
                'content' => 'Сам себе отвечу',
            ])
            ->assertCreated();

        Queue::assertNothingPushed();
    }
```

И добавляется третий — про саму задачу. HTTP-запрос здесь не нужен: задача это обычный класс, её можно создать и выполнить руками.

```php
    /**
     * Задача проверяется отдельно от контроллера: это разные вопросы, и смешивать
     * их в одном тесте значит получить тест, который падает по двум причинам сразу.
     *
     * Никакого Queue::fake() здесь нет и быть не должно — мы не ставим задачу
     * в очередь, а выполняем её handle() напрямую, как это сделал бы воркер.
     */
    public function test_job_sends_mail_to_post_author(): void {
        Mail::fake();

        $comment = Comment::factory()->for($post, 'commentable')->create();

        (new SendCommentMailJob($post, $comment))->handle();

```

Четвёртый тест (`test_mail_shows_post_title_and_comment`) не меняется вовсе: он рендерит Mailable напрямую и про очередь ничего не знает.

О `Queue::fake()` и `Bus::fake()`: первый подменяет очередь и ловит задачи методом `assertPushed()`, второй подменяет шину команд и ловит их через `assertDispatched()`. Для обычной задачи годятся оба; `Bus::fake()` понадобится, когда дело дойдёт до пачек — у него есть `assertBatched()`.

## 21. Каст `published_at` у `Post`

Маленькая тема с конца урока, и она закрывает реальный пробел в проекте.

У `Comment` каст даты стоит с 25-го урока, у `Post` — нет. Поэтому `$post->published_at` сейчас возвращает строку, и любая попытка обратиться к ней как к дате падает:

```php
$post->published_at->diffForHumans();   // Call to a member function diffForHumans() on string
$post->created_at->diffForHumans();     // работает: created_at Laravel кастует сам
```

Каст — это правило «в каком виде отдавать атрибут на уровне PHP». В базе ничего не меняется, преобразование происходит при чтении и обратно при записи.

В `app/Models/Post.php`, рядом с `$fillable`:

```php
    /**
     * published_at — не строка, а момент времени. Каст превращает его в Carbon
     * при чтении и обратно при записи, а в JSON он уходит в ISO-8601 —
     * ровно так же, как это давно сделано у Comment.
     *
     * @return array<string, string>
     */
    protected function casts(): array {
        return [
            'published_at' => 'datetime',
        ];
    }
```

Альтернатива касту — аксессор (`protected function publishedAt(): Attribute`), но он требует писать преобразование руками и, если оставить то же имя атрибута, конфликтует сам с собой. Каст короче и делает ровно то, что нужно. Кроме `datetime` часто применяют `boolean`, `array`, `decimal:2` и касты в enum.

**Что при этом изменится в интерфейсе.** `PostResource` отдаёт `published_at` как есть, и формат в JSON станет другим: было `2026-06-28 11:20:01`, стало `2026-06-28T11:20:01.000000Z`. В `Admin/Post/Index.vue` функция `formatDate()` делает `value.replace(' ', 'T')` — на новой строке эта замена просто ничего не находит, и `new Date(...)` разбирает её без проблем. А вот показанное время сдвинется на часовой пояс браузера, и это **исправление, а не поломка**: приложение живёт в UTC (`config/app.php`), раньше UTC-время показывалось как будто оно местное. Проверьте эту колонку глазами после правки.

## 23. Грабли

- **Задачи копятся в `jobs`, писем нет** — не запущен воркер. Самая частая причина: приложение подняли не через `composer run dev`, а отдельно, и `queue:listen` никто не запустил.
- **Всё работает мгновенно и без воркера** — в `.env` стоит `QUEUE_CONNECTION=sync`. Задача выполняется прямо в запросе, очереди фактически нет.
- **`Typed property ... must not be accessed before initialization`** — воркер `queue:work` держит в памяти старую версию класса. `php artisan queue:restart`, а в разработке — `queue:listen`.
- **`MaxAttemptsExceededException`** — задача была зарезервирована умершим воркером. Смотрите `reserved_at` и `attempts` в `jobs`: строка «зависла» в занятом состоянии.
- **Воркер работает, задача в `jobs` лежит и не берётся** — у неё другое имя очереди. Воркер без `--queue` разбирает только `default`.
- **`ModelNotFoundException` в `failed_jobs`** — пост или комментарий удалили раньше, чем воркер взял задачу. `SerializesModels` достаёт модели из базы заново. Для уведомления это правильное поведение.
- **Задача обрывается ровно через минуту** — упёрлись в `--timeout=60`. Поднимите таймаут флагом или свойством `$timeout` на классе.
- **Письмо приходит дважды** — задача упала после отправки (например, на `dd()` или на чём-то после `Mail::send()`), и повтор отправил письмо заново. Задача должна быть устроена так, чтобы повтор был безопасен, либо `$tries = 1`.
- **Тест зелёный, хотя `dispatch()` из контроллера удалён** — в тесте нет `Queue::fake()`, а драйвер `sync` выполняет всё синхронно. Проверяется отправка письма, а не постановка задачи.
- **`Queue::assertPushed()` падает, хотя всё работает в браузере** — забыт `Queue::fake()` **до** запроса. После запроса подменять уже нечего.
- **`schedule:list` пуст или команды нет** — запись не в `routes/console.php` либо ошибка в сигнатуре: первым аргументом `Schedule::command()` идёт ровно то, что пишут после `php artisan`.
- **`schedule:work` запущен, а команда не выполняется** — ждите начала следующей минуты: расписание срабатывает по границе минуты, а не в момент запуска.
- **На проде расписание не работает** — в crontab нет строки с `schedule:run`, либо в ней относительный путь. Путь к проекту должен быть абсолютным: вне проекта слово `artisan` системе ничего не говорит.
- **Cron шлёт письма после каждого запуска** — в строке crontab не выброшен вывод: нужен хвост `>> /dev/null 2>&1`.
- **На проде воркер «иногда перестаёт работать»** — его запустили руками по SSH. Процесс живёт до конца сессии; нужен Supervisor с `autorestart=true`.
- **После деплоя воркеры выполняют старый код** — забыт `php artisan queue:restart` в скрипте деплоя.
- **Сервер задыхается после настройки Supervisor** — слишком большой `numprocs`. Каждый воркер держит в памяти всё приложение; начинайте с двух-четырёх.
- **Время публикации в админке сдвинулось на несколько часов** — это следствие каста `published_at`, и оно корректное: приложение работает в UTC, а браузер показывает местное время.

## 25. Что можно сделать лучше

**Очередь для всей ветки уведомлений.** Сейчас в очередь уходит одна конкретная задача. Когда появится событие `CommentCreated` и несколько слушателей, фоновым станет весь набор реакций разом — достаточно `ShouldQueue` на слушателях.

**Отдельная очередь под письма.** `->onQueue('mail')` и свой воркер: тогда ночная выгрузка не задержит уведомление, а тяжёлая задача не займёт единственного воркера.

**Повторы с умом.** `$tries = 3` и `$backoff = [10, 30, 60]` для письма — разумная настройка: недоступный минуту SMTP-сервер не должен стоить пользователю уведомления.

**Чистка таблиц.** `failed_jobs` и `job_batches` растут и сами не убираются. В расписании для этого есть `queue:prune-failed` и `queue:prune-batches` — типичная запись `->daily()`.

**Laravel Horizon.** Для Redis-очередей есть отдельная панель: очереди, воркеры, время выполнения, упавшие задачи, метрики — всё в браузере вместо `select * from failed_jobs`. Для проекта на `database`-драйвере не подходит, но знать о ней стоит: это стандартный ответ на вопрос «как смотреть за очередями на проде».

**`withoutOverlapping()` для будущей статистики.** Как только появится ежедневная команда, стоит сразу защитить её от наложения запусков — иначе долгий подсчёт однажды встретится сам с собой.
