# Lesson 19 - Фильтр списка постов без кнопки

Цель урока: поставить над таблицей постов фильтр по заголовку, дате публикации и минимальному числу лайков — и сделать так, чтобы список обновлялся сразу после изменения поля, без кнопки «Найти».

По пути разбираются: переиспользование `AbstractFilter`/`PostFilter` из 13-го урока в админке, фильтрация по количеству связанных записей (`has()`), один экшен, отдающий два формата ответа (Inertia-страница и JSON), локальная копия пропса в `data()`, `watch` с `deep: true` и debounce.

Отправная точка — состояние после 18-го урока: посты создаются и редактируются, `Index.vue` показывает таблицу, `PostController::index()` отдаёт Inertia-страницу.

## 1. Что уже готово: фильтр из 13-го урока

Ничего нового изобретать не нужно — механизм фильтрации в проекте есть с 13-го урока, он просто использовался только в API. Напомним, из чего он состоит:

- `App\Filters\AbstractFilter` — общий алгоритм: пройти по списку разрешённых ключей `$keys` и для каждого пришедшего вызвать одноимённый метод.
- `App\Filters\PostFilter` — список ключей и по методу на каждый; каждый метод добавляет своё условие в `Builder`.
- `App\Models\Traits\HasFilter` — scope `filter()`, который сам находит класс фильтра по имени модели (`Post` → `PostFilter`).
- `App\Http\Requests\Api\Post\IndexRequest` — валидация query-параметров.

Ключевая мысль урока: **фильтр не привязан к API**. Это обычный scope, `Post::query()->filter($data)` работает в любом контроллере. Меняется только одно — какой Request проверяет входные данные. У админки будет свой, потому что у неё другой контракт (об этом п.3).

Что нужно доделать: из трёх полей формы два (`title`, `published_at_from`) в `PostFilter` уже есть, третьего (`likes_from`) — нет.

## 2. `likes_from`: фильтр по количеству связанных записей

Лайк в проекте — это строка в `likeables` (полиморфная связь многие-ко-многим, 12-й урок). У поста есть связь:

```php
public function likedByProfiles(): MorphToMany {
    return $this->morphToMany(Profile::class, 'likeable')->withTimestamps();
}
```

Значит «постов с лайками не меньше N» — это не условие по колонке, а условие по **количеству записей в связи**.

IN `app/Filters/PostFilter.php`:
```php
protected array $keys = [
    'id',
    'author_id',
    'category_id',
    'category_title',
    'title',
    'content',
    'img_path',
    'status',
    'likes_from',
    'published_at_from',
    'published_at_to',
    'created_at_from',
    'created_at_to',
    'updated_at_from',
    'updated_at_to',
];
```

```php
/**
 * Посты, у которых лайков не меньше указанного числа.
 *
 * has() строит подзапрос-счётчик по связи, поэтому колонка likes_count в posts не нужна.
 */
protected function likesFrom(Builder $builder, int|string $value): void {
    $builder->has('likedByProfiles', '>=', (int) $value);
}
```

Что здесь изучается:

- **Ключ и метод связаны через `Str::camel()`.** `AbstractFilter::apply()` берёт ключ `likes_from`, превращает его в `likesFrom` и вызывает этот метод. Забыть добавить ключ в `$keys` — фильтр молча не сработает; ошибиться в имени метода — получить `Call to undefined method`. Это цена соглашения «имя метода = ключ», принятого в 13-м уроке.
- **`has('relation', '>=', N)`** — самый прямой способ фильтровать по количеству связанных записей. Laravel собирает коррелированный подзапрос:

  ```sql
  select * from "posts"
  where (
      select count(*) from "profiles"
      inner join "likeables" on "profiles"."id" = "likeables"."profile_id"
      where "likeables"."likeable_id" = "posts"."id"
        and "likeables"."likeable_type" = 'App\Models\Post'
  ) >= 3
  ```

  Проверить руками: временно поставить `->dumpRawSql()` вместо `->get()` в контроллере.
- **Родня `has()`.** `has('rel')` без операторов — «хотя бы одна запись» (`>= 1`). `doesntHave('rel')` — «ни одной». `whereHas('rel', fn ($q) => ...)` — то же, что `has()`, но с дополнительными условиями внутри подзапроса (например, «лайки только от активных профилей»). Нам хватает голого `has()`.
- **Почему не `withCount()` + `having()`.** Соблазн написать `->withCount('likedByProfiles')->having('liked_by_profiles_count', '>=', $value)` есть, но в PostgreSQL это упадёт: `HAVING` не умеет ссылаться на алиас из `SELECT` (в отличие от MySQL, где такой код работает). Пришлось бы дублировать весь подзапрос внутри `having` или заворачивать всё во внешний подзапрос. `has()` от диалекта не зависит — ещё один повод не проверять фильтры на SQLite, если проект живёт на PostgreSQL.
- **Приведение типа `(int) $value`.** Из query-строки всё приезжает строками, даже после правила `integer` (валидатор проверяет, но не кастует). Поэтому в фильтре тип-хинт `int|string` и явный каст — так же, как у соседних `id()` и `status()`.
- **Производительность.** Подзапрос выполняется для каждой строки `posts`. Спасает индекс, который `$table->morphs('likeable')` создал в миграции `likeables` — по паре `(likeable_type, likeable_id)`. На учебных объёмах это неважно, но знать, за счёт чего работает, полезно.

Фильтры `title` и `published_at_from` уже написаны в 13-м уроке, менять их не нужно:

```php
protected function title(Builder $builder, string $value): void {
    $builder->where('title', 'ilike', "%{$value}%");
}

protected function publishedAtFrom(Builder $builder, string $value): void {
    $builder->where('published_at', '>=', $value);
}
```

`ilike` — оператор PostgreSQL: поиск без учёта регистра. В MySQL его нет (там `like` и так регистронезависим при обычной collation) — это место придётся править при смене СУБД.

## 3. `Admin\Post\IndexRequest`

`php artisan make:request Admin/Post/IndexRequest`

IN `app/Http/Requests/Admin/Post/IndexRequest.php`:
```php
<?php

namespace App\Http\Requests\Admin\Post;

use Illuminate\Contracts\Validation\ValidationRule;
use Illuminate\Foundation\Http\FormRequest;

class IndexRequest extends FormRequest {
    public function authorize(): bool {
        return true;
    }

    /**
     * Три поля формы фильтра. Ровно три — контракт админки уже, чем у API:
     * чего нет здесь, того не будет и в validated(), а значит, и в фильтре.
     *
     * @return array<string, ValidationRule|array<mixed>|string>
     */
    public function rules(): array {
        return [
            'title' => ['nullable', 'string', 'max:255'],
            // <input type="date"> шлёт «2026-06-01» — без времени, в отличие от API.
            'published_at_from' => ['nullable', 'date_format:Y-m-d'],
            // min:0, а не min:1: «лайков не меньше нуля» — валидный, пусть и бесполезный запрос.
            'likes_from' => ['nullable', 'integer', 'min:0'],
        ];
    }
}
```

Что здесь изучается:

- **Отдельный Request, а не переиспользование `Api\Post\IndexRequest`.** Классы одноимённые, но контракты разные: API принимает 14 параметров и требует дату в формате `Y-m-d H:i:s`, админская форма шлёт три параметра и дату без времени. Общий класс пришлось бы обвешивать условиями. То же разделение уже принято для `StoreRequest`/`UpdateRequest` в 15-м и 18-м уроках: пространство имён `Admin` против `Api`.
- **`PostFilter` при этом один на двоих.** Метод `publishedAtFrom()` не знает, `Y-m-d` ему пришло или `Y-m-d H:i:s` — он просто подставляет строку в `where`, а PostgreSQL приводит её к `timestamp` (для `2026-06-01` это `2026-06-01 00:00:00`). Разграничение форматов — задача валидации, а не фильтра. Это удачное разделение ответственности: контракт задаёт Request, поведение — фильтр.
- **Всё `nullable`, ничего `required`.** Фильтр по определению необязателен: пустая форма должна отдавать полный список, а не 422.
- **Валидация query-параметров — это тоже защита.** Без Request в `filter()` уехало бы `$request->all()`, то есть любой параметр из адресной строки. `AbstractFilter` спасает белым списком `$keys`, но полагаться на один слой не стоит: `max:255` и `integer` отсекают мусор до похода в БД.

### Почему пустое поле не ломает фильтр

Это главная тонкость урока, без которой «фильтр без кнопки» работать не будет.

Форма отправляет **все три поля всегда**, в том числе незаполненные. То есть в запросе будет `?title=&published_at_from=&likes_from=`. Пустая строка — не то же самое, что отсутствие параметра: правило `nullable` её не пропустит (`''` не проходит `date_format`), а фильтр по заголовку превратился бы в `ilike '%%'`.

Спасает пара глобальных middleware, которые Laravel держит в стеке по умолчанию:

- `Illuminate\Foundation\Http\Middleware\TrimStrings` — обрезает пробелы по краям всех строковых полей;
- `Illuminate\Foundation\Http\Middleware\ConvertEmptyStringsToNull` — превращает `''` в `null`.

Дальше цепочка складывается сама:

```
?title=          →  ConvertEmptyStringsToNull  →  null
                 →  правило nullable           →  валидация пройдена
                 →  validated() = ['title' => null, ...]
                 →  isset($data['title'])      →  false
                 →  метод title() не вызван
```

Ключевое звено — `isset()` в `AbstractFilter::apply()`: он возвращает `false` и для отсутствующего ключа, и для `null`. Поэтому незаполненное поле просто не участвует в запросе.

Проверить, что middleware на месте, можно в `bootstrap/app.php`: если в `withMiddleware()` нет ни `$middleware->remove([...])`, ни своего `$middleware->use([...])`, значит используется стандартный набор.

## 4. Один экшен — два формата ответа

Список постов теперь запрашивается двумя разными способами: при заходе на страницу — обычным Inertia-переходом, при изменении фильтра — запросом axios. Отдельный маршрут для второго случая заводить не нужно: URL и данные те же, отличается только упаковка ответа.

IN `app/Http/Controllers/Admin/PostController.php`:
```php
use App\Http\Requests\Admin\Post\IndexRequest;

/**
 * Список постов для админки — он же источник данных для фильтра.
 *
 * Отдаёт два формата по одному URL: Inertia-страницу при обычном переходе
 * и голый JSON при запросе от axios.
 *
 * @return array<int, array<string, mixed>>|Response
 */
public function index(IndexRequest $request): array|Response {
    // category грузим заранее: без eager loading каждая строка таблицы дала бы
    // отдельный запрос (N+1), а whenLoaded в ресурсе просто не отдал бы связь.
    // withCount добавляет к каждому посту liked_by_profiles_count одним подзапросом.
    $posts = Post::query()
        ->filter($request->validated())
        ->with('category')
        ->withCount('likedByProfiles')
        ->latest('id')
        ->get();

    $posts = PostResource::collection($posts)->resolve();

    // Отличает запросы заголовок Accept: axios шлёт application/json,
    // Inertia — text/html. Проверку делаем до inertia(), иначе axios
    // получит HTML целой страницы вместо массива постов.
    if ($request->wantsJson()) {
        return $posts;
    }

    return inertia('Admin/Post/Index', compact('posts'));
}
```

Что здесь изучается:

- **`wantsJson()` против `expectsJson()`.** `wantsJson()` смотрит на **первый** тип в заголовке `Accept`: если клиент предпочитает JSON — отдаём JSON. `expectsJson()` мягче — он вернёт `true` ещё и для любого AJAX-запроса (`X-Requested-With: XMLHttpRequest`), который не просит явно HTML. Здесь разница принципиальна: Inertia отправляет `Accept: text/html, application/xhtml+xml` **и** `X-Requested-With: XMLHttpRequest`, поэтому `expectsJson()` на инертийном переходе может дать `true` и сломать страницу. `wantsJson()` смотрит только на `Accept` и отвечает правильно.
- **Откуда `Accept` у axios.** Он ставит `Accept: application/json, text/plain, */*` по умолчанию — руками ничего добавлять не нужно. Именно на это опирался и 18-й урок, когда объяснял, почему ошибки валидации приходят JSON-ом, а не редиректом.
- **`$request->wantsJson()`, а не `request()->wantsJson()`.** Хелпер `request()` достанет тот же объект из контейнера, но в сигнатуре метода запрос уже есть — брать его повторно из глобального состояния незачем. Явная зависимость лучше неявной: метод честно показывает, от чего зависит, и его проще тестировать.
- **Составной тип возврата `array|Response`.** Метод возвращает либо массив (Laravel сам сериализует его в JSON), либо `Inertia\Response`. PHP 8 позволяет объявить union-тип — это лучше, чем убрать тип-хинт совсем.
- **`filter()` первым в цепочке — по вкусу, но осмысленно.** Порядок вызовов на итоговый SQL не влияет (Builder копит условия), но читается лучше так: сначала «что выбираем», потом «что подгружаем», потом «как сортируем».
- **`with('category')` и `latest('id')` никуда не делись.** При переписывании `index()` их легко потерять — и получить N+1 и случайный порядок строк. Сортировка особенно заметна: без `latest('id')` PostgreSQL не обещает никакого порядка вообще, и после фильтрации список может «перемешаться».

Маршрут менять не нужно — `GET /admin/posts` объявлен ещё в 15-м уроке:

```php
Route::get('/admin/posts', [PostController::class, 'index'])->name('admin.posts.index');
```

## 5. Колонка «Лайки»

Отдельная маленькая задача, без которой фильтр по лайкам нечем проверить: количество лайков нужно вывести в таблицу.

IN `app/Http/Resources/Post/PostResource.php`:
```php
'published_at' => $this->published_at,
// whenCounted — брат whenLoaded для withCount(): ключ появится в ответе,
// только если счётчик действительно посчитан. Имя атрибута ресурс выведет
// сам: likedByProfiles → liked_by_profiles_count.
'likes_count' => $this->whenCounted('likedByProfiles'),
```

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<th class="px-4 py-3 text-left font-medium">Опубликован</th>
<th class="px-4 py-3 text-left font-medium">Лайки</th>
<th class="px-4 py-3 text-right font-medium">Действия</th>
```

```vue
<td class="whitespace-nowrap px-4 py-4 text-gray-500">
    {{ post.likes_count ?? 0 }}
</td>
```

Колонок стало восемь — значит, снова правим `colspan` у строки-заглушки (в 18-м уроке он уже менялся с 6 на 7):

```vue
<tr v-if="!postsData.length">
    <td colspan="8" class="px-4 py-10 text-center text-gray-500">
        Публикаций пока нет.
    </td>
</tr>
```

Что здесь изучается:

- **`whenCounted()` работает по тому же принципу, что `whenLoaded()`.** Если `withCount()` не вызывали, атрибута `liked_by_profiles_count` у модели нет, и ключ `likes_count` просто не попадёт в ответ. Поэтому на страницах `Show` и `Edit`, где счётчик не считается, ресурс не сломается — там ключа не будет вовсе.
- **Отсюда `?? 0` в шаблоне.** `undefined` вывелся бы в ячейку пустотой. Оператор объединения с null даёт понятный ноль. Заодно это напоминание, что ключ в ответе не гарантирован — ровно как `post.category` уже проверяется через `v-if`.
- **Имя ключа в ресурсе — не имя атрибута.** В БД и модели атрибут называется `liked_by_profiles_count`, наружу отдаём короткое `likes_count`. Ресурс для того и нужен: внутреннее представление и внешний контракт — разные вещи.
- **`withCount()` не делает второго запроса.** Он добавляет подзапрос в `SELECT`, поэтому счётчик приезжает вместе с постами. Это не тот же подзапрос, что построил `has()` в фильтре: их будет два — один в `select`, другой в `where`.

## 6. Форма фильтра в `Index.vue`

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<Link
    :href="route('admin.posts.create')"
    class="mb-4 inline-block border border-sky-800 bg-sky-700 px-3 py-2 text-xs text-white hover:bg-sky-800"
>
    Создать
</Link>

<!--
    Фильтр без кнопки: элемента submit здесь нет вообще, запрос уходит
    по изменению любого поля (п.9). Обёртку <form> не ставим сознательно —
    без неё Enter в текстовом поле не может случайно перезагрузить страницу.
-->
<div class="mb-4 grid grid-cols-1 gap-3 bg-white p-4 sm:grid-cols-3">
    <label class="block">
        <span class="mb-1 block text-xs uppercase tracking-wider text-gray-500">
            Заголовок
        </span>
        <input
            v-model="filter.title"
            type="text"
            placeholder="часть заголовка"
            class="w-full border border-gray-300 px-3 py-2 text-sm"
        />
    </label>

    <label class="block">
        <span class="mb-1 block text-xs uppercase tracking-wider text-gray-500">
            Опубликован с
        </span>
        <input
            v-model="filter.published_at_from"
            type="date"
            class="w-full border border-gray-300 px-3 py-2 text-sm"
        />
    </label>

    <label class="block">
        <span class="mb-1 block text-xs uppercase tracking-wider text-gray-500">
            Лайков не меньше
        </span>
        <input
            v-model.number="filter.likes_from"
            type="number"
            min="0"
            class="w-full border border-gray-300 px-3 py-2 text-sm"
        />
    </label>
</div>
```

Что здесь изучается:

- **Имена полей — snake_case.** В JS это выглядит непривычно, но `filter` — не внутреннее состояние компонента, а **набор query-параметров**: его ключи уезжают в URL как есть и обязаны совпасть с ключами в `rules()` и в `PostFilter::$keys`. Три места, где имя должно быть одинаковым: `data()`, Request, фильтр. Переименовывать — сразу во всех трёх.
- **`<input type="date">`** даёт браузерный date picker и всегда отдаёт в `v-model` строку вида `2026-06-01`, независимо от того, как дата показана пользователю (в русской локали — `01.06.2026`). Именно поэтому в правилах стоит `date_format:Y-m-d`.
- **`v-model.number`** просит Vue привести введённое к числу. Модификатор здесь скорее для порядка: числом или строкой `"3"` приедет `likes_from`, правило `integer` пропустит оба, а фильтр всё равно делает `(int)`. Полезно знать поведение на краю: при пустом поле `.number` возвращает не `null`, а пустую строку — и её опять превратит в `null` серверный `ConvertEmptyStringsToNull`.
- **`<label>` оборачивает `<input>`.** Клик по подписи ставит фокус в поле — доступность бесплатно, без пары `for`/`id`.
- **Почему без `<form>`.** Форма с одним текстовым полем сабмитится по Enter, и браузер уйдёт GET-запросом на текущий URL, перезагрузив страницу. Ставить `<form @submit.prevent>` ради этого незачем — проще не заводить форму.

Ещё две правки в шаблоне — заменить источник данных для таблицы и счётчика (почему именно `postsData`, разбирается в следующем пункте):

```vue
<span class="text-sm text-gray-500">Всего: {{ postsData.length }}</span>
```

```vue
<tr
    v-for="post in postsData"
    :key="post.id"
    class="align-top transition-colors hover:bg-gray-50"
>
```

## 7. `postsData`: локальная копия пропса

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<script>
export default {
    props: {
        posts: {
            type: Array,
            default: () => [],
        },
    },
    data() {
        return {
            // Ключи совпадают с правилами IndexRequest и с $keys у PostFilter.
            filter: {
                title: '',
                published_at_from: '',
                likes_from: null,
            },
            // Что показывает таблица. Изначально — то, что приехало пропсом;
            // после фильтрации — ответ сервера. Пропс менять нельзя, поэтому копия.
            postsData: this.posts,
            // Ссылка на отложенный вызов filterPosts() (см. п.9).
            timerId: null,
        };
    },
};
</script>
```

Что здесь изучается:

- **Пропсы доступны только для чтения.** Это следствие однонаправленного потока данных во Vue: пропс принадлежит родителю (здесь — Inertia, которая отдала его с сервера), и менять его снизу нельзя. Попытка присвоить `this.posts = res.data` даст предупреждение `Avoid mutating a prop directly` и сломается при следующем обновлении родителя. Поэтому заводим своё состояние `postsData`, а пропс остаётся исходным значением.
- **`this` внутри `data()` работает.** Пропсы инициализируются раньше `data()`, поэтому `this.posts` уже доступно. Обратное неверно: из `props` до `data` не достучаться.
- **Это копия ссылки, а не глубокая копия.** `postsData: this.posts` даёт **тот же самый массив**. Безопасно это только потому, что мы всегда **заменяем** `postsData` целиком (`this.postsData = res.data`), а не мутируем. Напиши мы `this.postsData.push(...)` или `.sort()` — изменился бы и массив пропса. Нужна независимость — `[...this.posts]`.
- **Снимок не следит за пропсом.** Если `posts` изменится позже (например, Inertia сделает partial reload), `postsData` останется старым. Лечится наблюдателем:

  ```js
  watch: {
      posts(value) {
          this.postsData = value;
      },
  },
  ```

  Сейчас это не нужно — пропс приходит один раз, при заходе на страницу, — но знать про рассинхронизацию полезно: это классический баг «данные на сервере обновились, а на экране старые».
- **`timerId` в `data()`** делает поле реактивным, хотя реактивность ему не нужна: шаблон его не читает. Хранить такое можно и вне `data()` (например, завести в хуке `created()`), но для учебного кода лишняя сущность дороже лишней реактивности.

## 8. `filterPosts()`: запрос через axios

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<script>
import axios from 'axios';

export default {
    methods: {
        filterPosts() {
            axios.get(route('admin.posts.index'), {
                params: this.filter,
            })
                .then(res => {
                    // res.data — массив из PostResource::collection()->resolve().
                    this.postsData = res.data;
                })
                .catch(e => {
                    // 422 — ошибка в значениях фильтра. Список оставляем как есть:
                    // затирать его пустым массивом при ошибке хуже, чем не делать ничего.
                    console.log(e.response?.data);
                });
        },
    },
};
</script>
```

Что здесь изучается:

- **`params` вместо ручной сборки строки.** Второй аргумент `axios.get()` — конфиг запроса, `params` — объект, который axios сам превратит в query-строку и закодирует значения (`?title=%D0%BB%D0%B0%D1%80%D0%B0%D0%B2%D0%B5%D0%BB%D1%8C&likes_from=3`). Собирать URL конкатенацией не нужно: забытый `encodeURIComponent()` ломается на первом же пробеле или символе `&` в заголовке.
- **Что axios делает с пустыми значениями.** Параметры со значением `null` или `undefined` он **пропускает** — их в URL не будет. А вот пустая строка отправляется (`title=`). Итог: часть полей отсекается на клиенте, часть — серверным `ConvertEmptyStringsToNull` (п.3). Оба пути ведут к одному: фильтр по этому ключу не применится.
- **`route('admin.posts.index')` от Ziggy** отдаёт полный URL текущего домена, а `params` дописывает query-строку. Хардкодить `/admin/posts` не нужно — то же соглашение, что и в 15–18-м уроках.
- **GET, а не POST.** Фильтр ничего не меняет на сервере, значит по семантике HTTP это GET. Практическое следствие: CSRF-токен не нужен (он проверяется только для «изменяющих» методов), а ответ в принципе кешируем.
- **Метод возвращает JSON, а страница не перерисовывается.** Inertia в этом запросе не участвует вообще: заголовка `X-Inertia` нет, история браузера не трогается, компонент не пересоздаётся. Меняется ровно одна переменная `postsData` — и Vue сам перерисовывает `<tbody>`.
- **`e.response?.data`** — опциональная цепочка на случай, когда ответа нет вовсе (обрыв сети, отменённый запрос): у такой ошибки axios поля `response` не будет. Разбиралось в 18-м уроке.

## 9. Без кнопки: `watch`, `deep` и debounce

Вторая задача урока: список должен обновляться сразу после изменения поля, без кнопки. Осталось решить, **что вызывает** `filterPosts()`.

IN `resources/js/Pages/Admin/Post/Index.vue`:
```vue
<script>
export default {
    watch: {
        filter: {
            // Отменяем предыдущий отложенный вызов и ставим новый:
            // запрос уйдёт через 400 мс после последнего нажатия клавиши.
            handler() {
                clearTimeout(this.timerId);
                this.timerId = setTimeout(this.filterPosts, 400);
            },
            // Без deep наблюдатель не увидит изменение filter.title:
            // сам объект filter при этом остаётся тем же самым.
            deep: true,
        },
    },
};
</script>
```

Что здесь изучается:

- **`watch` — четвёртый ключ Options API рядом с `props`, `data`, `methods`.** Он вызывает функцию, когда наблюдаемое значение изменилось. Короткая форма — `watch: { filter() { ... } }`, полная — объект с `handler` и опциями (`deep`, `immediate`).
- **`deep: true` обязателен.** По умолчанию Vue сравнивает старое и новое значение по ссылке. `filter` — объект; при вводе текста меняется его свойство `title`, а ссылка на объект остаётся прежней, и наблюдатель не сработает. `deep: true` заставляет Vue отслеживать вложенные свойства. Цена — обход всего объекта при каждом изменении; для трёх полей это ничто.
- **Один наблюдатель вместо трёх обработчиков.** Альтернатива — повесить `@input="filterPosts"` на каждое поле. Работает, но требует не забыть обработчик на каждом новом поле фильтра; наблюдатель за объектом покрывает все поля разом, включая те, что появятся позже.
- **`immediate: true` нам не нужен.** С ним handler выполнился бы сразу при создании компонента — и страница сделала бы второй, точно такой же запрос за списком, который уже приехал пропсом.
- **Debounce — не украшение, а необходимость.** Без него ввод «laravel» отправит семь запросов: по одному на букву. Шесть из них бесполезны, но каждый — полный проход по БД с подзапросом по лайкам. `setTimeout` + `clearTimeout` — минимальная реализация: каждое новое нажатие отменяет предыдущий отложенный вызов, запрос уходит, когда пользователь перестал печатать на 400 мс.
- **`setTimeout(this.filterPosts, 400)`, а не `setTimeout(this.filterPosts(), 400)`.** Передаём саму функцию, а не результат её вызова. Со скобками запрос ушёл бы немедленно, а через 400 мс `setTimeout` попытался бы вызвать `undefined`. Стрелочная обёртка `() => this.filterPosts()` тоже подойдёт и в общем случае надёжнее — она сохраняет `this`; здесь это не важно, потому что методы Vue уже привязаны к экземпляру компонента.
- **Значение 400 мс** — компромисс: меньше 200 мс почти не даёт эффекта, больше секунды воспринимается как «залипание». Для полей `date` и `number`, где ввод «атомарный», задержка избыточна, но заводить ради них отдельный путь без debounce не стоит.

## 10. Что осталось за кадром

Не задачи этого урока, но честные ограничения текущей реализации.

**Гонка ответов.** Debounce уменьшает число запросов, но не гарантирует порядок ответов. Если запрос по «lar» пойдёт медленно, а следующий по «laravel» — быстро, то в `postsData` в итоге ляжет результат первого: он придёт последним. Лечится счётчиком запросов:

```js
data() {
    return {
        lastRequestId: 0,
    };
},
methods: {
    filterPosts() {
        const requestId = ++this.lastRequestId;

        axios.get(route('admin.posts.index'), { params: this.filter })
            .then(res => {
                // Ответ на устаревший запрос игнорируем: пока он шёл, ушёл более свежий.
                if (requestId === this.lastRequestId) {
                    this.postsData = res.data;
                }
            });
    },
},
```

Более взрослый вариант — отменять предыдущий запрос через `AbortController` (axios понимает его как `signal`), тогда сервер и сеть не тратятся впустую.

**Фильтр не попадает в URL.** Состояние живёт только в компоненте: обновление страницы, кнопка «назад» и ссылка, отправленная коллеге, фильтр не сохранят. Для Inertia это решается штатно — `router.get(url, params, { preserveState: true, replace: true, only: ['posts'] })`: адрес меняется, компонент не пересоздаётся, а с сервера приезжает только пропс `posts`.

**Инертийный способ вместо axios.** Тот же `router.get()` с `only: ['posts']` снял бы сразу три вещи: ветку `wantsJson()` в контроллере, локальную копию `postsData` и рассинхронизацию с URL — сервер обновлял бы пропс напрямую. Мы этого не делаем сознательно, по той же причине, что и в 18-м уроке с `useForm()`: сначала механика на голом axios (что уходит в запросе, что приходит в ответе, кто хранит состояние), потом инструменты, которые её прячут.

**Пагинация.** `->get()` тянет все совпавшие посты. Когда постов станет много, `->paginate(20)` изменит форму ответа (появятся `data`, `links`, `meta`) — и `postsData = res.data` придётся заменить на `res.data.data`. Тема отдельного урока.

**Индикатор загрузки.** Между нажатием клавиши и обновлением таблицы проходит полсекунды, и всё это время на экране старые данные без каких-либо признаков, что идёт запрос. Флаг `loading` в `data()`, выставляемый перед запросом и снимаемый в `.finally()`, — минимальная честная обратная связь.

## 11. Грабли

- **Фильтр по лайкам молча не работает, ошибок нет.** Метод `likesFrom()` написан, но ключ `likes_from` не добавлен в `$keys` у `PostFilter`. `apply()` ходит по списку ключей, а не по методам класса.
- **`Call to undefined method App\Filters\PostFilter::likes_from()`** — обратная ситуация: ключ добавлен, а метод назван в snake_case. `AbstractFilter` приводит ключ к camelCase через `Str::camel()`.
- **422 при выборе даты.** Правило скопировано из `Api\Post\IndexRequest` вместе с `date_format:Y-m-d H:i:s`, а `<input type="date">` шлёт `2026-06-01`. Смотреть вкладку **Network**: в Payload видно, что именно уехало.
- **`column "liked_by_profiles_count" does not exist`** — фильтр написан через `withCount()` + `having()`. В PostgreSQL `HAVING` не видит алиасы из `SELECT`. Использовать `has()`.
- **В `res.data` приходит HTML целой страницы, а таблица разваливается на отдельные символы.** В контроллере забыт `wantsJson()`: без заголовка `X-Inertia` метод `inertia()` рендерит корневой Blade-шаблон. `postsData` становится строкой, а `v-for` по строке перебирает символы.
- **Каждая буква — отдельный запрос в Network.** Не сделан debounce либо `clearTimeout()` вызывается не для того идентификатора.
- **Наблюдатель не срабатывает вообще.** Забыт `deep: true` — изменение свойства внутри объекта `filter` не меняет ссылку на сам объект.
- **Список моргает и возвращается к предыдущему результату.** Гонка ответов (п.10): пришёл ответ на устаревший запрос.
- **`Avoid mutating a prop directly` в консоли** — в `.then()` осталось `this.posts = res.data` вместо `this.postsData`.
- **Таблица обновляется, а «Всего: N» в шапке — нет.** В заголовке остался `posts.length`.
- **Пустая форма отдаёт пустой список или 422.** Отключён `ConvertEmptyStringsToNull` — пустые поля приезжают строками `''`, не проходят `date_format` и превращают поиск по заголовку в `ilike '%%'`.
- **После фильтрации в логах десятки запросов к `categories`.** При переписывании `index()` потерян `with('category')` — вернулся N+1.
- **Порядок постов после фильтрации «случайный»** — потерян `latest('id')`. PostgreSQL без `ORDER BY` порядок строк не гарантирует.
- **Строка «Публикаций пока нет» съехала или не появляется** — не поправлен `colspan` (теперь 8) или в `v-if` остался `posts` вместо `postsData`.
- **В колонке лайков пусто вместо нулей** — забыт `?? 0`, либо в контроллере нет `withCount('likedByProfiles')`, и `whenCounted()` не отдал ключ.
