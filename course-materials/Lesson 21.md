# Lesson 21 - Ошибки формы, удаление поста, кэширование списка

Цель урока: довести админку постов до состояния «форма честно отвечает пользователю, список умеет удалять, а тяжёлый запрос не выполняется на каждый чих». Три сюжета независимы, но в конце сталкиваются лбами: кэш из третьего прячет результат удаления из второго — и это самое полезное, что в уроке есть.

По пути разбираются: форма ответа 422 и почему `errors` — это массивы; ключи вида `images.0`; очистка ошибок при вводе; `nextTick` и почему DOM обновляется не сразу; маршрут `DELETE` и ответ 204; полиморфные связи без внешних ключей и ручная уборка; `Cache::remember`, TTL и ключ из `md5(serialize())`; `serializable_classes` в Laravel 13; инвалидация кэша на драйвере `database`, где нет тегов.

Отправная точка — состояние после 20-го урока: `Create.vue` отправляет форму и молча гасит ошибку в `console.log`; `Index.vue` умеет фильтровать и листать; `PostController::index()` на каждый запрос ходит в базу.

## 1. Что приходит с 422 и почему сообщений на поле несколько

`StoreRequest` не проходит валидацию → `ValidationException` → обработчик исключений видит, что запрос `wantsJson()`, и отдаёт 422 с телом такой формы:

```json
{
    "message": "The title field is required. (and 2 more errors)",
    "errors": {
        "title": [
            "The title field must not be greater than 255 characters.",
            "The title has already been taken."
        ],
        "content": ["The content field is required."],
        "images.0": ["The images.0 field must be an image."]
    }
}
```

Что здесь изучается:

- **`errors` — это «поле → массив сообщений», а не «поле → строка».** Массив не для красоты: валидатор проверяет **все** правила поля и складывает все провалы. Заголовок в 300 символов, который вдобавок уже занят, провалит и `max:255`, и `unique:posts,title` — два сообщения на одно поле. Показывать только первое — значит заставлять пользователя чинить форму в несколько заходов.
- **Когда проверка всё-таки останавливается досрочно.** `Validator::shouldStopValidating()` прерывает перебор правил поля в трёх случаях: есть правило `bail` и уже случилась ошибка; провалилось правило `uploaded` (файл не долетел — проверять его размер бессмысленно); провалилось «неявное» правило вроде `required` (поля нет — остальные правила применять не к чему). Во всех прочих случаях сообщений будет столько, сколько правил не прошло.
- **`message` — это первое сообщение плюс счётчик.** Годится как заголовок («что-то не так»), но не как текст рядом с полем: конкретика лежит в `errors`.
- **Ключ ошибки — путь до значения, а не имя поля.** Для элементов массива Laravel строит ключи `images.0`, `images.1`, `tags.2` — по одному на провалившийся элемент. Ключа `images` в ответе при этом не будет вовсе. Это ломает наивный `errors['images']` и разбирается в п.3.
- **Почему 422, а не 400.** 422 Unprocessable Entity — «синтаксис запроса понят, но значения не годятся». Клиенту это позволяет отличить «поправь данные» от «сломан запрос» и от «упал сервер», не разбирая тело ответа.

## 2. Показ ошибок в `Create.vue`

`Edit.vue` умеет это с 18-го урока, но показывает по одному сообщению на поле (`this.errors[field]?.[0]`). В `Create.vue` делаем сразу правильно — списком.

IN `resources/js/Pages/Admin/Post/Create.vue`:
```html
<input
    v-model="post.title"
    placeholder="title"
    class="mb-1 w-full border border-gray-200 p-4"
    @input="clearFeedback('title')"
/>
<p
    v-for="error in errors.title"
    :key="error"
    class="mb-1 text-xs text-red-600"
>
    {{ error }}
</p>
```

Что здесь изучается:

- **`errors.title` — уже массив, и он идёт прямо в `v-for`.** Метода-геттера не нужно: ошибки мы храним ровно в том виде, в каком показываем, — «поле → массив сообщений». Чтобы это было правдой и для картинок, ответ сервера приводится к такому виду на входе (п.3).
- **`v-for` вместо `v-if` с одним сообщением.** Список сам исчезает, когда массив пуст, — отдельная проверка не нужна.
- **Ошибок нет — `errors.title` равен `undefined`, и это нормально.** `v-for` по `undefined` во Vue 3 не падает и не рисует ничего. Написать `errors.title ?? []` можно для явности, но обязательным это не является.
- **`:key="error"` — сама строка сообщения.** Внутри одного поля сообщения не повторяются, так что текст годится в ключи. Индекс тоже подошёл бы: список перерисовывается целиком и не сортируется.
- **`mb-1` у поля вместо `mb-4`.** Отступ переезжает на сообщение: иначе текст висел бы далеко от поля, к которому относится, а без ошибок появлялся бы двойной зазор.
- **Почему не переиспользуется `InputError.vue`.** Компонент от Breeze лежит в `Components/`, но принимает **одну строку** в проп `message` и написан на `<script setup>`. Он под другую задачу — форму профиля, где на поле приходит одно сообщение. Натягивать его сюда пришлось бы через переделку пропа в массив, то есть менять компонент чужого модуля ради нашего. Пока проще держать разметку в странице; общий компонент имеет смысл заводить, когда таких форм станет три (см. п.17).

## 3. Ошибки массивов: ключ `images.0`

Правило `images.*` порождает ошибку на каждый элемент отдельно. Если пользователь выбрал три файла и второй оказался PDF, в ответе будет только `images.1` — а `errors.images` останется `undefined`, и `v-for` из п.2 не покажет ничего.

Чинить это можно двумя способами. Первый — искать ключи по префиксу в каждом месте, где ошибки читаются: в шаблоне, в очистке полей. Тогда формат сервера с точками расползается по всему компоненту. Второй — привести ответ к своему виду один раз, на входе. Делаем второй:

IN `resources/js/Pages/Admin/Post/Create.vue`:
```js
/**
 * Сворачивает ключи ответа к именам полей: images.1 и images.2 → images.
 *
 * Вызывается один раз, в handleError(). Дальше вся форма работает с простым
 * «поле → массив сообщений», и ни шаблон, ни clearFeedback() про точки не знают.
 */
groupErrors(errors) {
    const grouped = {};

    for (const [key, messages] of Object.entries(errors)) {
        const field = key.split('.')[0];

        grouped[field] = [...(grouped[field] ?? []), ...messages];
    }

    return grouped;
},
```

Было `{ "title": [...], "images.1": [...], "images.2": [...] }` — стало `{ title: [...], images: [сообщение про второй файл, сообщение про третий] }`.

Что здесь изучается:

- **Чужой формат приводим к своему на границе.** Общий приём, не только про валидацию: там, где данные приходят извне, их стоит один раз переложить в форму, удобную приложению, а не подстраиваться под источник в каждой точке использования. Сложность остаётся в одном месте вместо трёх.
- **Сообщения не теряются, а склеиваются.** `[...(grouped[field] ?? []), ...messages]` добавляет новые сообщения к уже накопленным. Ошибки по второму и третьему файлу окажутся в одном массиве и выведутся двумя абзацами — ровно как показал бы сервер.
- **`key.split('.')[0]` — имя поля до первой точки.** `images.1` → `images`, `title` → `title`. Одно выражение покрывает и обычные поля, и элементы массивов; отдельной ветки не нужно.
- **Номер файла остаётся виден пользователю.** Laravel подставляет ключ в текст: «The images.1 field must be an image». По-английски и с индексом от нуля — для учебного проекта терпимо; лечится файлом `lang/ru/validation.php` и ключом `attributes` (см. п.17).
- **Что теряется при свёртке.** Машинная привязка сообщения к номеру файла. Пока картинки — один `input[type=file] multiple` без превью, привязывать сообщение не к чему. Если появятся миниатюры выбранных файлов и захочется подсветить красным именно вторую, понадобится другая свёртка — `{ images: { 1: [...], 2: [...] } }` — или исходные ключи сервера.

## 4. Очистка ошибок при изменении полей

Красная подпись под полем, которое пользователь уже исправил, — враньё интерфейса: сервер этого текста больше не присылал.

IN `resources/js/Pages/Admin/Post/Create.vue`:
```js
/**
 * Гасит всю обратную связь по полю, как только пользователь начал его править:
 * сообщения об ошибке, общую плашку и «Пост создан».
 *
 * delete по ключу реактивного объекта во Vue 3 работает штатно: data() отдана
 * под Proxy, у которого есть ловушка deleteProperty. Во Vue 2 для этого нужен
 * был Vue.delete / this.$delete — в Vue 3 таких хелперов больше нет.
 *
 * Одна строка вместо перебора ключей — заслуга groupErrors() из п.3: ключ
 * images в errors один, а не images.0, images.1 и images.2 по отдельности.
 */
clearFeedback(field) {
    delete this.errors[field];

    this.message = '';
    this.isSuccess = false;
},
```

Вызывается из самих полей — там, где происходит ввод:

```html
<input v-model="post.title" @input="clearFeedback('title')" />
<textarea v-model="post.content" @input="clearFeedback('content')"></textarea>
<select v-model="post.category_id" @change="clearFeedback('category_id')">
<input ref="imagesInput" type="file" multiple @change="handleImages" />
<textarea v-model="tags" @input="clearFeedback('tags')"></textarea>
```

Что здесь изучается:

- **`@input` для текста, `@change` для `select` и файлов.** `input` летит на каждый символ; у `select` и `input[type=file]` его нет — значение меняется целиком, и событие называется `change`.
- **Точечная очистка, а не `this.errors = {}`.** Обнулять всё разом проще, но тогда правка заголовка уберёт с экрана и жалобу на пустой контент — пользователь решит, что всё в порядке, и отправит форму второй раз впустую.
- **Выбрали новые файлы — уходят все сообщения по картинкам сразу.** Держать их по отдельности смысла нет: выбор файлов заменяет весь список целиком, старые претензии относятся к файлам, которых в форме больше нет.
- **Альтернатива через `watch`.** Можно было завести `watch: { post: { handler() {…}, deep: true } }` вместо обработчиков в разметке — на скриншоте курса сделано именно так. Обработчик честнее: он различает, какое поле изменилось, а глубокий наблюдатель за объектом — нет, и `images` с `tags` лежат вне `post`, так что наблюдателей понадобилось бы три. Но главное отличие не в этом — см. пункт о программной очистке ниже.
- **`message` и `isSuccess` гасим заодно.** Общая плашка «Проверьте заполнение полей» после первой же правки перестаёт быть правдой. «Пост создан» — тоже: пользователь уже пишет следующий пост, и сообщение о прошлом на экране только мешает.
- **Программная очистка формы сюда не попадает — и это важно.** `resetForm()` присваивает `this.post = {…}` из кода, а события `input` и `change` порождает браузер в ответ на действие пользователя. Присваивание их не вызывает, поэтому очистка формы после успешной отправки `clearFeedback()` не запустит и только что показанную плашку не погасит. С наблюдателем за объектом так не выйдет: он реагирует на состояние и не знает, кто его изменил (разбор в п.5).

## 5. Сообщение об успехе и `nextTick`

IN `resources/js/Pages/Admin/Post/Create.vue`:
```html
<p
    v-if="isSuccess"
    ref="success"
    class="mb-4 border border-green-200 bg-green-50 p-3 text-sm text-green-700"
>
    Пост создан.
</p>
```

```js
/**
 * Показывает плашку «Пост создан» и подводит к ней экран.
 *
 * Vue не трогает DOM в момент присваивания: изменения складываются в очередь
 * и применяются пачкой в следующем «тике». nextTick() — обещание, которое
 * исполняется после того, как очередь разобрана и DOM уже перерисован.
 */
async showSuccess() {
    this.isSuccess = true;

    // Тик нужен ровно для следующей строки: элемент создаётся через v-if, и сразу
    // после присваивания this.$refs.success ещё undefined — прокручивать нечего.
    await this.$nextTick();

    this.$refs.success?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
},
```

Гасится плашка не здесь, а в `storePost()` — вместе с ошибками, ещё до отправки запроса (п.6):

```js
this.errors = {};
this.message = '';
this.isSuccess = false;
this.saving = true;
```

Что здесь изучается:

- **Реактивность асинхронна.** Присваивание меняет данные немедленно, а DOM — нет. Любой код, которому нужен уже перерисованный DOM (ссылка `ref`, измерение размеров, прокрутка, установка фокуса), обязан идти внутри `nextTick`.
- **`$nextTick()` без аргумента возвращает промис.** Отсюда `await` вместо лесенки из вложенных колбэков. Форма `this.$nextTick(() => …)` тоже жива и делает то же самое.
- **Тик — это микрозадача, а не пауза в миллисекундах.** Внутри `nextTick()` — обычный `Promise.resolve().then(…)`: очередь разбирается сразу, как только текущий синхронный код досчитал до конца, и всегда **до** того, как браузер нарисует кадр. Секунд у тика нет, это позиция в очереди задач, а не задержка.
- **Отсюда: `false` и `true` через `nextTick` не мигают.** Оба присваивания уложатся в один кадр, и состояния «плашки нет» браузер не нарисует ни разу — оно существует только в памяти. Чтобы пропадание стало видимым, между ним и появлением должна пройти настоящая задача. У нас она есть — запрос к серверу.
- **Поэтому один тик, а не два.** Напрашивается сбросить `isSuccess` в `false` прямо здесь: вторая отправка иначе присвоит `true` поверх `true`, Vue сравнит значения и не перерисует ничего. Но сбрасывать тут уже нечего — флаг погашен в `storePost()` перед запросом, и к моменту `.then()` плашки на экране нет. Остаётся честный переход `false` → `true`, и Vue его нарисует. Единственный оставшийся тик нужен не для показа, а для прокрутки.
- **Гашение при отправке честнее сброса при показе.** Пока запрос в полёте, надпись «Пост создан» относится к прошлому посту и перестала быть правдой: чем кончится текущая отправка, ещё неизвестно. По той же причине рядом гасятся `errors` и `message`. Заодно `saving = true` блокирует кнопку сразу — пользователь видит, что клик засчитан, не дожидаясь ответа.
- **`?.` у `$refs.success`.** Дешёвая страховка: поменяют разметку, `ref` исчезнет — метод не упадёт с `TypeError`.
- **`isSuccess`, а не текст в `message`.** Успех и ошибка — разные состояния: ошибка приходит с сервера списком по полям, успех — это один флаг. Один общий стринг заставил бы хранить рядом ещё и «какого он цвета». Гаснут они, впрочем, вместе — в `clearFeedback()` при правке поля и в `storePost()` перед отправкой.

**На скриншоте курса это сделано иначе.** Там показ плашки отложен на тик, а гашения перед запросом нет:

```js
.then(res => {
    this.entries.post = { title: '', description: '', content: '', category_id: null }

    nextTick(() => {
        this.isSuccess = true
    })
})
```

`nextTick` здесь не лишний — он обходит собственный `watch` компонента. Порядок такой:

1. `this.entries.post = {…}` меняет объект формы и ставит в очередь задачу наблюдателя;
2. очередь разбирается — наблюдатель видит изменение и гасит `isSuccess`;
3. только после этого отложенный колбэк ставит `isSuccess = true`, и гасить его уже некому.

Без `nextTick` порядок обратный: флаг поднимается синхронно, а наблюдатель отрабатывает следом и опускает его обратно — плашка не появляется вовсе.

Что из этого следует для нас:

- **У нас та же логика, но без обхода.** Плашку мы тоже гасим при изменении полей — в `clearFeedback()` на `@input` и `@change` (п.4). Разница в том, чем это вызвано: событие приходит от пользователя, а `resetForm()` его не порождает. Поэтому наша очистка формы плашку не трогает, поднимать флаг можно сразу, и откладывать показ не нужно.
- **Наблюдатель отличает состояние, событие отличает действие.** Это и есть причина расхождения. `watch` видит «объект стал другим» и не знает, кто его изменил, — программная очистка для него неотличима от ввода. Обработчик `@input` привязан к действию пользователя, и лишних срабатываний у него нет.
- **Форма записи тоже отличается.** В лекции `nextTick(cb)` — функция, импортируемая из `vue`; у нас `await this.$nextTick()` — то же самое, доступное в Options API без импорта и без вложенного колбэка. Разница чисто стилистическая.
- **Обе версии одинаково молчат при второй отправке.** `nextTick` эту проблему не решает: он не пересекает границу кадра. Решает гашение в `storePost()`.

## 6. Итоговый `<script>` в `Create.vue`

IN `resources/js/Pages/Admin/Post/Create.vue`:
```js
data() {
    return {
        post: {
            title: '',
            content: '',
            category_id: null,
        },
        images: [],
        tags: '',
        // Ошибки по полям, уже свёрнутые к именам полей: { title: [...], images: [...] }.
        errors: {},
        // Общая плашка над формой: и для 422, и для всего остального.
        message: '',
        // Плашка «Пост создан».
        isSuccess: false,
        // Запрос в полёте: блокирует кнопку до ответа сервера.
        saving: false,
    };
},
methods: {
    groupErrors(errors) {
        const grouped = {};

        for (const [key, messages] of Object.entries(errors)) {
            const field = key.split('.')[0];

            grouped[field] = [...(grouped[field] ?? []), ...messages];
        }

        return grouped;
    },
    clearFeedback(field) {
        delete this.errors[field];

        this.message = '';
        this.isSuccess = false;
    },
    handleImages(event) {
        this.images = Array.from(event.target.files);
        this.clearFeedback('images');
    },
    storePost() {
        if (this.saving) {
            return;
        }

        const formData = new FormData();

        Object.entries(this.post).forEach(([key, value]) => {
            formData.append(key, value ?? '');
        });

        this.images.forEach((image) => {
            formData.append('images[]', image);
        });

        formData.append('tags', this.tags);

        // Чистим обратную связь перед новой попыткой: и ошибки прошлого раза,
        // и зелёную плашку — иначе рядом с новой ошибкой висело бы «Пост создан».
        // Гашение здесь же избавляет showSuccess() от сброса флага: пока идёт
        // запрос, плашка снята, и ответ вернёт её честным переходом false → true.
        this.errors = {};
        this.message = '';
        this.isSuccess = false;
        this.saving = true;

        axios
            .post(route('admin.posts.store'), formData)
            .then(() => {
                this.resetForm();
                this.showSuccess();
            })
            .catch(this.handleError)
            // finally, а не разблокировка в каждой ветке: в отличие от Edit.vue
            // мы остаёмся на странице, никакой router.visit() кнопку не переживает.
            .finally(() => {
                this.saving = false;
            });
    },
    resetForm() {
        // Форму чистим только после подтверждения сервера: при ошибке введённые
        // данные должны остаться, чтобы их можно было исправить.
        this.post = {
            title: '',
            content: '',
            category_id: null,
        };
        this.images = [];
        this.tags = '';
        // input[type=file] сам не сбрасывается — только через ref.
        this.$refs.imagesInput.value = '';
    },
    async showSuccess() {
        this.isSuccess = true;
        await this.$nextTick();

        this.$refs.success?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
    },
    handleError(error) {
        // response? обязателен: если запрос не дошёл до сервера (обрыв сети, CORS),
        // у ошибки axios поля response нет вовсе, и обработчик упал бы с TypeError.
        if (error.response?.status === 422) {
            // Единственное место, где формат сервера превращается в наш (п.3).
            this.errors = this.groupErrors(error.response.data.errors);
            this.message = 'Проверьте заполнение полей';

            return;
        }

        // 419, 500, обрыв сети. Показывать response.data.message от 500-й нельзя:
        // при APP_DEBUG=true туда попадает текст исключения с внутренностями приложения.
        this.message = 'Не удалось создать пост. Попробуйте ещё раз.';
    },
},
```

Что здесь изучается:

- **`.catch(this.handleError)`, а не `.catch((e) => this.handleError(e))`.** Метод компонента уже привязан к экземпляру — Vue делает это при инициализации, так что `this` внутри не потеряется. Обёртка ничего не добавляет.
- **Три флага вместо одного.** `saving` — про запрос, `errors` и `message` — про отказ, `isSuccess` — про успех. Каждый гасится в своё время, и это тот случай, когда четыре свойства понятнее одного «состояния формы» с перечислением.
- **Порядок в `.then()`: сначала очистка, потом плашка.** `resetForm()` синхронный, `showSuccess()` — асинхронный из-за `await`. Наоборот тоже сработало бы, но читается хуже: сначала убрали, потом сообщили.

## 7. Удаление поста: маршрут и контроллер

IN `routes/web.php`:
```php

// в URL не нужно. Подмена метода через _method здесь не требуется: запрос уходит
// не из HTML-формы, а из axios, а он умеет любой глагол.
```

IN `app/Http/Controllers/Admin/PostController.php`:
```php

 * Удаление поста.
 *
 * Алиас в импорте нужен из-за коллизии: в этом файле Response — это Inertia\Response,
 * его возвращают страницы. Здесь ответ обычный HTTP-шный.
 *
 * 204 No Content: тела у ответа нет — клиенту нечего показывать, он и так знает,
 * какой пост удалял. Возвращать удалённую модель обратно — распространённая,
 * но бессмысленная привычка: этих данных больше не существует.

    return response()->noContent();
```

Что здесь изучается:

- **Ресурсная конвенция закрыта.** `index`, `create`, `store`, `show`, `edit`, `update`, `destroy` — семь стандартных экшенов, и последний из них появляется сейчас. Имена не выдуманы: по ним `Route::resource()` в будущем сгенерирует ровно эти же маршруты.

- **Авторизации пока нет.** Сейчас удалить любой пост может любой залогиненный пользователь. Это дыра, и закрывается она политикой (`PostPolicy::delete()`), а не проверкой в контроллере, — но политики идут дальше по курсу.

## 8. `PostService::destroy()`: полиморфные связи не каскадятся

IN `app/Services/PostService.php`:
```php
/**
 * Удаление поста вместе со всем, что к нему привязано.
 *
 * Полиморфные связи живут без внешних ключей: morphs() создаёт два обычных
 * столбца (imageable_type, imageable_id) и индекс по ним — FOREIGN KEY тут
 * невозможен, потому что родитель у строки не один. Значит, никакого
 * ON DELETE CASCADE от PostgreSQL не будет: удалив только строку posts,
 * мы оставим в images, taggables, likeables и comments висячие записи,
 * указывающие на несуществующий пост. Ошибки не случится — случится мусор.
 *
 * Уборку делаем руками, по одной связи, и в транзакции: удаление поста —
 * это пять запросов, и оборваться посередине оно не должно.
 */
public static function destroy(Post $post): void {
    DB::transaction(function () use ($post): void {
        // Картинки — через тот же сервис, что и в update(): он удалит строки,
        // а файлы сотрёт с диска только после успешного коммита.
        ImageService::deleteBatch($post->images()->pluck('id')->all(), $post);

        // detach() без аргументов снимает все связи разом — это DELETE по taggables
        // и likeables. Сами теги и профили остаются: это общие справочники,
        // они принадлежат не посту, а приложению.
        $post->tags()->detach();
        $post->likedByProfiles()->detach();

        // Комментарии без поста не имеют смысла, поэтому удаляются вместе с ним.
        // each->delete(), а не ->delete() одним запросом: так срабатывают события
        // Eloquent, а с ними логирование из трейта HasLog.
        $post->comments->each->delete();

        $post->delete();
    });
}
```

Что здесь изучается:

- **Каскад бывает трёх видов, и здесь работает только третий.** Первый — на уровне БД (`->constrained()->cascadeOnDelete()`), для полиморфных связей недоступен. Второй — на уровне модели через событие `deleting`. Третий — руками в сервисе, как сейчас. Мы выбрали третий, потому что вся остальная логика поста уже живёт в `PostService`, и разносить её по двум местам ради одного метода рано (вариант с событием — в п.17).
- **`detach()` против `delete()`.** У связи «многие ко многим» удалять нужно строки промежуточной таблицы, а не связанные модели. `$post->tags()->delete()` удалил бы сами теги из справочника — вместе со всеми их привязками к другим постам.
- **`pluck('id')->all()` перед `deleteBatch()`.** Сервис из 18-го урока принимает список id, а не модели: сигнатуру не меняем ради нового вызывающего, если старая подходит.
- **Файлы удаляются после коммита.** Это уже заложено в `ImageService::deleteBatch()` через `DB::afterCommit()`: откат транзакции вернёт строки в базу, но не файлы на диск, поэтому стирать их раньше коммита нельзя.
- **`$post->comments`, а не `$post->comments()`.** Без скобок — это загруженная коллекция моделей, по ней и работает `each->delete()`. Со скобками был бы билдер, и `->delete()` снёс бы строки одним запросом мимо событий.
- **Чего этот код всё-таки не убирает.** У комментария есть свои картинки, теги, лайки и вложенные ответы. Удаляя комментарий поштучно, мы поднимаем его события, но обработчика уборки у `Comment` нет — его мусор останется. Честная рекурсивная уборка — задача для событий модели (п.17).

```js
destroyPost(post) {
    // Удаление необратимо, поэтому спрашиваем. confirm() — заглушка: он блокирует
    // вкладку и выглядит по-разному в разных браузерах, но пока честнее
    // самодельного модального окна, которое пришлось бы писать с нуля (п.17).
    if (! confirm(`Удалить пост «${post.title}»?`)) {
        return;
    }

    this.deletingId = post.id;

    axios
        .delete(route('admin.posts.destroy', post.id))
        .then(() => this.reloadAfterDelete())
        .catch((e) => {
            console.log(e.response?.data);
        })
        .finally(() => {
            this.deletingId = null;
        });
},
```

Что здесь изучается:

- **`route('admin.posts.destroy', post.id)` даёт только URL.** Глагол задаёт вызов axios — `axios.delete(...)`. Ziggy про метод маршрута ничего не сообщает: перепутаете `delete` с `post` — получите 405 (см. п.15).
- **Ответ пустой.** Сервер вернул 204, `res.data` будет пустой строкой. Обращаться к ней не за чем, поэтому в `.then()` аргумент не принимаем вовсе.
- **`.finally()` для снятия блокировки.** Кнопка должна ожить и после успеха, и после ошибки: страница остаётся на месте в обоих случаях.

## 10. После удаления список надо перезапросить, а не поправить

В задании к уроку предложен очевидный вариант — выкинуть пост из массива на клиенте:

```js
this.posts = this.posts.filter(postItem => postItem.id !== post.id)
```

Он работает ровно один экран и разваливается на следующем:

```js
/**
 * Перезапрашивает список после удаления.
 *
 * Локальный filter() выкинул бы строку из таблицы, но всё остальное осталось бы
 * от прежнего ответа: «Всего: 13» вместо 12, пять кнопок страниц вместо четырёх,
 * четыре записи на странице вместо пяти — шестая, которая должна была подняться
 * со следующей страницы, на клиент просто не приезжала. Пересобрать meta на клиенте
 * нельзя: сервер считает total отдельным запросом count(*).
 */
reloadAfterDelete() {
    // Удалили единственную запись на не первой странице — этой страницы больше нет,
    // и сервер честно вернёт пустой список с current_page = 3. Отступаем назад;
    // наблюдатель за pagination сам вызовет отложенный запрос.
    if (this.postsData.data.length === 1 && this.entries.pagination.page > 1) {
        this.entries.pagination.page -= 1;

        return;
    }

    // Без debounce: клик по «Удалить» — однократное действие, а не набор текста.
    this.filterPosts();
},
```

Что здесь изучается:

- **Данные и метаданные приезжают вместе — и чинить их надо вместе.** Как только у списка появились `meta.total` и `meta.links`, любая правка коллекции на клиенте рассинхронизирует её с этими числами. Ответ сервера — единственный источник правды.
- **Проверка `length === 1` делается до перезапроса.** В этот момент удалённый пост ещё лежит в `postsData.data`: единица означает «на экране была ровно одна строка, и мы её только что снесли».
- **Условие `page > 1`.** На первой странице отступать некуда — пустой список там законен: постов действительно не осталось, и `v-if="!postsData.data.length"` покажет «Публикаций пока нет».
- **Присваивание вместо прямого вызова.** Меняем `entries.pagination.page` — срабатывает наблюдатель из 20-го урока и сам зовёт `scheduleFilterPosts()`. Дублировать запрос руками не нужно.
- **Прямой `filterPosts()`, а не `scheduleFilterPosts()`.** Debounce в 400 мс придуман для ввода символов; на клик по кнопке он даёт только видимую задержку.

## 11. Кэширование списка: `Cache::remember`

Каждый заход в список — это `count(*)` плюс выборка, а с фильтром по лайкам ещё и коррелированный подзапрос. Пока постов десяток, это незаметно; смысл упражнения — увидеть механику.

IN `app/Http/Controllers/Admin/PostController.php`:
```php
use Illuminate\Support\Facades\Cache;

$cacheKey = 'posts_index_'.md5(serialize($data));

$posts = Cache::remember($cacheKey, now()->addMinutes(120), function () use ($data) {
    return Post::query()
        ->filter($data['filters'] ?? [])
        ->with('category')
        ->withCount('likedByProfiles')
        ->latest('id')
        ->paginate($data['pagination']['per_page'], ['*'], 'page', $data['pagination']['page']);
});
```

Что здесь изучается:

- **`remember($key, $ttl, $callback)` — это «get или посчитай и положи».** Есть значение по ключу — вернуть его и замыкание не выполнять; нет — выполнить, положить с указанным сроком жизни, вернуть. Три строки вместо ручной связки `has()` / `get()` / `put()`, и без гонки между проверкой и чтением.
- **TTL принимает и число, и дату.** Число — секунды, `now()->addMinutes(120)` — момент, когда запись протухнет. Второй вариант читается лучше, и в задании к уроку он же.
- **Замыкание выполняется лениво.** Пока значение в кэше, запрос к базе не строится вообще — `Post::query()` внутри `remember()` просто не вызывается.
- **Где стоит `Cache::remember` — важно.** Он оборачивает запрос к базе, а не весь экшен: валидация, ветка `wantsJson()` и Inertia остаются снаружи. Кэшировать нужно дорогую часть, а не всё подряд.
- **Драйвер у нас `database`** (`CACHE_STORE=database`, таблица `cache` из стандартной миграции). Значение хранится сериализованной строкой в колонке `value`, срок жизни — unix-временем в `expiration`. Это самый медленный из практичных драйверов, но он не требует ставить Redis, и для учебного проекта его достаточно.

## 12. Ключ кэша: `md5(serialize($data))`

У кэша один ключ — одно значение. Список постов зависит от фильтра, номера страницы и её размера, значит и ключей должно быть столько же, сколько различимых наборов параметров.

```php
$cacheKey = 'posts_index_'.md5(serialize($data));
```

Что здесь изучается:

- **`serialize()` превращает массив в строку без потерь** — с типами и вложенностью, в отличие от `implode()` или `http_build_query()`. Два разных набора фильтров дадут две разные строки.
- **`md5()` — чтобы получить короткий ключ фиксированной длины,** а не ради безопасности. Сериализованный массив фильтров легко перевалит за сотню символов, а у ключей кэша есть ограничения: memcached режет на 250 байтах, у нас ключ — первичный ключ таблицы `cache`. 32 hex-символа снимают вопрос. Коллизий md5 тут можно не бояться: подбирать их некому.
- **Порядок ключей в массиве влияет на результат,** и это работает только потому, что `$data` приходит из `validated()`. Тот собирает результат, обходя `rules()`, — то есть порядок ключей задан кодом реквеста и одинаков для всех запросов. Клади мы в `serialize()` сырой `$request->all()`, порядок диктовал бы клиент, и `?page=2&per_page=5` дал бы не тот ключ, что `?per_page=5&page=2`.
- **Префикс `posts_index_` обязателен.** Голый `md5(serialize($data))` — это ключ без имени: другой контроллер, применивший ту же схему к такому же массиву, получит тот же ключ и молча прочитает чужое значение. Имя списка в ключе делает пространство имён явным.
- **Чего в ключе нет — и когда это станет дырой.** Пользователя. Сейчас админский список одинаков для всех, и это верно. Но стоит появиться правилу «автор видит только свои посты» — и первый зашедший положит в кэш свою выборку, а второй прочитает её как свою. Правило простое: всё, от чего зависит результат, обязано быть в ключе.
- **Общий префикс приложения добавляется поверх.** `config/cache.php` подставляет `Str::slug(APP_NAME).'-cache-'`, так что в таблице ключ будет выглядеть как `line-cache-posts_index_ab12…`. Это нужно, когда одну базу или один Redis делят несколько приложений.

## 13. Грабля Laravel 13: `serializable_classes`

Код из п.11 отработает **один раз**. На втором запросе страница упадёт:

```
Error: The script tried to call a method on an incomplete object.
Please ensure that the class definition "Illuminate\Pagination\LengthAwarePaginator"
of the object you are trying to operate on was loaded _before_ unserialize() gets called
```

IN `config/cache.php` (значение по умолчанию в Laravel 13):
```php
'serializable_classes' => false,
```

Что здесь изучается:

- **Что это за настройка.** Все драйверы кэша складывают значения через `serialize()` и читают через `unserialize()`. В Laravel 13 чтение стало ограниченным: `DatabaseStore::unserialize()` вызывает `unserialize($value, ['allowed_classes' => $this->serializableClasses])`, а `false` означает «никаких классов». Любой объект возвращается из кэша как `__PHP_Incomplete_Class` — заглушка, у которой нельзя вызвать ни одного метода.
- **Зачем так сделали.** Защита от gadget chain: если утечёт `APP_KEY` и злоумышленник сможет подложить своё значение в кэш, `unserialize()` без ограничений позволит собрать цепочку вызовов из классов приложения и выполнить чужой код. Белый список классов эту дверь закрывает.
- **Почему падение отложенное и потому неприятное.** Первый запрос — промах кэша: замыкание выполнилось, вернуло настоящий пагинатор, страница отрисовалась. Всё «работает». Ломается второй запрос — уже попадание в кэш. Легко списать на что угодно, кроме кэша.
- **Правильное лечение — не класть в кэш объекты.**

IN `app/Http/Controllers/Admin/PostController.php`:
```php
$posts = Cache::remember($cacheKey, now()->addMinutes(120), function () use ($data): array {
    $paginator = Post::query()
        ->filter($data['filters'] ?? [])
        ->with('category')
        ->withCount('likedByProfiles')
        ->latest('id')
        ->paginate($data['pagination']['per_page'], ['*'], 'page', $data['pagination']['page']);

    // Ресурс разворачиваем внутри замыкания: в кэш уезжает готовый массив
    // { data, links, meta } — ни одного объекта, ни одной модели, ни одного Carbon.
    // response()->getData(true) — это тот же ответ, что ушёл бы в браузер,
    // но разобранный обратно в ассоциативный массив.
    return PostResource::collection($paginator)->response()->getData(true);
});

// Обе ветки получают одинаковый массив: JSON-ветке роутер сам сделает из него
// JsonResponse, Inertia положит его пропсом. Форма ответа не изменилась,
// Index.vue правок не требует.
return $request->wantsJson() ? $posts : inertia('Admin/Post/Index', compact('posts'));
```

  Сигнатура экшена при этом меняется на `array|Response`, а `PostResource::collection()` уезжает внутрь замыкания.

- **Побочная выгода.** На попадании в кэш пропускается не только поход в базу, но и работа ресурса: раньше `PostResource` пересобирал массив на каждый запрос, теперь готовый массив достаётся целиком.
- **Два обходных пути, которые делать не стоит.** Перечислить классы в `serializable_classes` — придётся описать весь граф (`LengthAwarePaginator`, `Eloquent\Collection`, `Post`, `Category`, `Illuminate\Support\Carbon`, …), и любой новый `with()` его тихо ломает. Поставить `'serializable_classes' => true` — вернуть поведение Laravel 12 и выключить защиту всему приложению ради одного места. Кэшировать данные, а не объекты — правило, которое верно и без этой настройки.
- **При реализации кода в комментарии привести для сравнения код из п. 11 и объяснить почему он сработает только один раз**

## 14. Инвалидация: кэш ссорится с остальным уроком

Список закэширован на два часа. Значит:

- создали пост — его нет в списке;
- отредактировали — в списке старый заголовок;
- удалили — строка на месте, и «Удалить» по ней вернёт 404.

Причём фильтр создаёт иллюзию, что всё чинится: набрали букву в поиске — новый набор параметров, новый ключ, промах кэша, свежие данные. Стёрли букву — вернулись к старому ключу и снова видите вчерашний список.

**Тегов у нас нет.** Штатный ответ Laravel — `Cache::tags(['posts'])->flush()` — на драйвере `database` не работает: теги поддерживают только `redis`, `memcached`, `array` и `octane`, остальные бросают `BadMethodCallException: This cache store does not support tagging`.

**Что работает на любом драйвере — версия в ключе.**

IN `app/Services/PostService.php`:
```php
/**
 * Версия списка постов. Любая запись увеличивает её на единицу, и все ключи
 * со старой версией мгновенно перестают находиться — а протухнут они сами,
 * каждый по своему TTL. Так снимается ограничение драйвера database:
 * тегов у него нет, а один общий счётчик — обычное значение в кэше.
 *
 * forever(), а не put(): у счётчика нет причин протухать.
 * Атомарности здесь нет — два одновременных сохранения могут дать одну и ту же
 * версию вместо двух. Для админки на одного человека это неважно; на нагрузке
 * есть Cache::increment(), но он требует, чтобы ключ уже существовал.
 */
public static function bumpIndexVersion(): void {
    Cache::forever('posts_index_version', self::indexVersion() + 1);
}

public static function indexVersion(): int {
    return Cache::get('posts_index_version', 1);
}
```

Вызывается в конце `store()`, `update()` и `destroy()` — уже после коммита транзакции, а в ключ версия попадает так:

```php
$cacheKey = 'posts_index_'.PostService::indexVersion().'_'.md5(serialize($data));
```

Что здесь изучается:

- **У кэша всегда две задачи, и вторая сложнее первой.** Положить — легко, вовремя выбросить — нет. «В программировании две трудные задачи: инвалидация кэша и придумывание имён» — шутка ровно про это.
- **TTL — не инвалидация, а страховка.** Он ограничивает, насколько долго данные могут врать в худшем случае. Ответ на вопрос «когда обновить» он не даёт.
- **`Cache::flush()` — грубая альтернатива.** Одна строка в `store()`/`update()`/`destroy()`, работает везде, но сносит кэш всего приложения: и справочники, и лимиты запросов, и всё, что появится позже. Для одной таблицы это перебор.
- **Инвалидация после коммита, а не внутри транзакции.** Сбросьте версию внутри `DB::transaction()`, откатитесь — и следующий запрос положит в кэш данные, которых в базе нет. Место вызова — после того, как транзакция закрылась.
- **Правильный вопрос — не «как сбросить», а «нужно ли кэшировать».** Админский список постов видит один человек, читает его редко, а ждёт от него точности. Кэш ему скорее вредит. Настоящий кандидат на `Cache::remember` — публичная лента, которую открывают тысячи и где секунда устаревания никого не смущает. В уроке мы кэшируем админку, потому что это единственный готовый список в проекте.

## 15. Как убедиться, что кэш работает

Не гадать, а посмотреть в трёх местах:

- **Таблица `cache`.** После первого запроса в ней появляется строка с ключом `line-cache-posts_index_…`. `SELECT key, expiration FROM cache` покажет и ключ, и время протухания.
- **Логи запросов.** Второй одинаковый запрос не должен порождать `select count(*)` и `select * from posts`. Проще всего смотреть через `php artisan pail` — он уже поднимается вместе с `composer run dev`.
- **`storage/logs/post/retrieved.log`.** Побочный, но самый наглядный признак: трейт `HasLog` пишет строку на каждую **прочитанную из базы** модель. Попадание в кэш моделей не создаёт — файл перестаёт расти. Заодно видно, во что обходится это логирование на списках.

Сбросить руками: `php artisan cache:clear` (весь кэш) или `php artisan cache:forget <ключ>` (одно значение).

## 16. Грабли

- **`Error: The script tried to call a method on an incomplete object`** — в кэш положили объект, а `config/cache.php` в Laravel 13 идёт с `'serializable_classes' => false`. Падает не первый запрос, а второй (п.13).
- **Созданный пост не появляется в списке; удалённый не исчезает** — кэш на 120 минут без инвалидации. Проверяется мгновенно: `php artisan cache:clear` и обновить страницу (п.14).
- **`BadMethodCallException: This cache store does not support tagging`** — `Cache::tags()` на драйвере `database`. Теги есть только у `redis`, `memcached`, `array` и `octane`.
- **Кэш «то работает, то нет»** — так и есть: у каждого набора фильтров свой ключ. Набрали символ в поиске — промах и свежие данные, стёрли — попадание и старые.
- **405 Method Not Allowed при удалении** — `axios.post()` вместо `axios.delete()`, либо маршрут объявлен через `Route::post()`. Ziggy отдаёт только URL и о методе ничего не знает.
- **419 при удалении** — истёкшая сессия. CSRF-заголовок axios подставляет сам из куки `XSRF-TOKEN`, но если куки нет (или домен другой), запрос до контроллера не дойдёт.
- **Строка исчезла, а «Всего:» не изменилось** — список поправили `filter()` на клиенте вместо перезапроса. `meta` осталась от прежнего ответа (п.10).
- **После удаления таблица пустая, хотя посты есть** — снесли единственную запись на последней странице и не отступили на страницу назад.
- **В базе остались картинки и теги удалённого поста** — забыли, что у полиморфных связей нет внешних ключей: ошибки не будет, будет мусор (п.8).
- **Файлы удалённого поста остались на диске** — картинки удалили запросом мимо `ImageService::deleteBatch()`. Строки исчезли, а `Storage::delete()` никто не вызвал.
- **Из справочника пропали теги** — вместо `$post->tags()->detach()` написано `$post->tags()->delete()`. Удалились сами теги, вместе с их привязками к другим постам.
- **Ошибки валидации не показываются** — читаете `error.response.data.message` (строка-заголовок) вместо `error.response.data.errors` (объект с массивами).
- **На поле видно только одно сообщение из двух** — `errors[field][0]` вместо `v-for` по массиву.
- **Ошибки картинок не показываются никогда** — ключ в ответе `images.0`, а не `images`, и `errors.images` равен `undefined`. Ответ нужно свернуть к именам полей в `groupErrors()` (п.3).
- **Плашка «Пост создан» не появляется во второй раз** — `isSuccess` остался `true` с прошлой отправки, а присваивание того же значения ничего не меняет. Гасить флаг нужно в `storePost()` перед запросом (п.5). Сброс через `nextTick` в момент показа не спасёт: оба присваивания уложатся в один кадр, и пропадания не будет видно.
- **Плашка «Пост создан» не появляется вообще** — обратная связь гасится глубоким `watch` на объекте формы, а `resetForm()` этот объект меняет: наблюдатель срабатывает на нашу же очистку и опускает флаг сразу после того, как его подняли. Лечится либо отложенным показом через `nextTick` (так в лекции), либо отказом от наблюдателя в пользу `@input` (так у нас, п.4).
- **`this.$refs.success` равен `undefined`** — обратились к элементу до перерисовки DOM. `ref` внутри `v-if` появляется только со следующим тиком.
- **`this.$delete is not a function`** — привычка из Vue 2. В Vue 3 обычный `delete obj.key` реактивен, а хелперов `$delete` и `$set` больше нет.
- **Ошибка исчезает и тут же возвращается** — `clearFeedback()` повешен на `@change` у текстового поля: событие приходит по потере фокуса, а не при вводе.

## 17. Что можно сделать лучше

Ниже — не задачи урока, а направления, куда эта реализация растёт.

**Уборка на событии модели, а не в сервисе.** `PostService::destroy()` работает, только если удаление идёт через сервис. `Post::destroy(5)` из тинкера, каскад из будущего удаления категории, массовый `->delete()` — всё это оставит мусор. Событие `deleting` срабатывает всегда:

```php
protected static function booted(): void {
    static::deleting(function (Post $post): void {
        $post->images->each->delete();
        $post->tags()->detach();
        $post->likedByProfiles()->detach();
        $post->comments->each->delete();
    });
}
```

Тот же обработчик на `Comment` сделает уборку рекурсивной: удаление поста снесёт комментарии, те — свои ответы и картинки. Это и есть штатный «каскад на уровне приложения» — правильный ответ для полиморфных связей.

**Мягкое удаление.** `SoftDeletes` вместо настоящего `DELETE`: колонка `deleted_at`, запись остаётся в базе, из выборок исчезает сама. Для контента, который создают пользователи, это почти всегда правильнее — ошибочное удаление можно отменить. Взамен нужно помнить про `withTrashed()` и следить, чтобы `unique` по `title` не блокировал новый пост уже удалённым.

**Политика на удаление.** Сейчас любой залогиненный пользователь удалит любой пост. `PostPolicy::delete(User $user, Post $post)` и `$this->authorize('delete', $post)` в экшене — стандартное место для такого правила. Тогда же на клиенте появится смысл прятать кнопку.

**Модальное окно вместо `confirm()`.** В `Components/` уже лежит `Modal.vue` от Breeze, и в `Profile/Partials/DeleteUserForm.vue` есть готовый пример подтверждения удаления. Своё окно не блокирует вкладку, выглядит одинаково во всех браузерах и позволяет написать нормальный текст.

**Русские сообщения валидации.** Сейчас пользователь видит «The images.0 field must be an image». Файл `lang/ru/validation.php` (создаётся `php artisan lang:publish`) плюс блок `attributes` с человеческими названиями полей превращают это в «Файл 1 должен быть изображением». Отдельный набор сообщений можно задать прямо в реквесте — методами `messages()` и `attributes()`.

**Общий компонент для ошибок поля.** `FieldErrors.vue` с пропом-массивом закроет и `Create.vue`, и `Edit.vue`, и все формы, которые появятся дальше. Заводить его стоит на третьей форме, не раньше: сейчас это было бы две строки разметки, спрятанные в отдельный файл.

**Автоскрытие плашки успеха.** `setTimeout(() => { this.isSuccess = false }, 4000)` с сохранением идентификатора таймера, чтобы вторая отправка отменила таймер первой. Без сохранения таймеры накопятся и погасят свежее сообщение раньше времени.

**Кэш там, где он нужен.** Публичная лента, счётчики на дашборде, справочник категорий — вот кандидаты. Для админского списка кэш скорее вреден: читает его один человек, а точность нужна сразу.

**`Cache::flexible()` вместо `remember()`.** Отдаёт слегка устаревшее значение мгновенно и пересчитывает его в фоне после отправки ответа. Пользователь не ждёт пересчёта на первом же запросе после протухания.

**Redis как драйвер кэша.** Даёт теги (`Cache::tags(['posts'])->flush()`), атомарные `increment()` и хранение в памяти вместо запросов в ту же базу, которую мы и разгружаем. Смена драйвера — одна строка в `.env`; весь код с `Cache::remember()` остаётся прежним. Это и есть смысл фасада `Cache`: приложение не знает, где лежат данные.

**Тест на удаление.** Feature-тест — `post()`, `delete()`, `assertDatabaseMissing('posts', …)` и `assertDatabaseMissing('taggables', …)` — фиксирует именно то, что легко сломать при рефакторинге: уборку связанных строк. Кэш в тестах при этом стоит держать на драйвере `array`, чтобы значения не переезжали между тестами.
